## A. 调研：四大"提出一个框架/工具"的论文是怎么写的

### A.0 看了哪些

全文读了 20 篇（PDF 在 `docs/参考论文/`，新增的 13 篇见文末清单），按和我们的相近程度分三组：

| 组 | 论文 | 为什么看 |
|---|---|---|
| ① 黑盒/服务端注入检测（最近邻） | Black Widow (S&P'21)、Witcher (S&P'23)、NAUTILUS (USENIX'23)、MINER (USENIX'23)、Atropos (USENIX'24)、Spider-Scents (USENIX'24)、RESTler (ICSE'19) | 同类问题，看结构和实验 |
| ② 用 LLM/智能体做检测的工具（方法近邻） | **AgentFuzz** (USENIX'25，智能体污点类漏洞)、**YuraScanner** (NDSS'25，LLM 智能体走多步流程的黑盒扫描器)、**LLMSmith** (CCS'24，LLM 应用 RCE 检测+实证)、ChatAFL (NDSS'24)、PentestGPT (USENIX'24)、Snipuzz (CCS'21，IoT 黑盒)、KernelGPT、Fuzz4All、GPTScan | 看"LLM 做组件"的论文怎么立论、怎么处理 LLM 的不确定性 |
| ③ 评测方法论（审稿人的尺子） | **SoK: Prudent Evaluation Practices for Fuzzing** (S&P'24)、**Dos and Don'ts of ML in Security** (USENIX'22)、Evaluating Fuzz Testing (CCS'18) | 审稿人拿来挑实验毛病的标准 |

### A.1 章节结构：两种主流排法

把 20 篇的章节标题抽出来对比（原始抽取见附录 A1），工具类论文几乎都落在下面两种排法之一：

**排法①"挑战驱动"（绝大多数：Atropos、Black Widow、AgentFuzz、NAUTILUS、Witcher、Snipuzz）**
```
1 Introduction
2 Background（+ Threat Model + 真实漏洞例子）
3 Challenges（或 Problem Statement / Motivation）
4 Design（Overview 一图 + 每个技术一小节，技术与挑战一一对应）
5 Implementation（很短）
6 Evaluation（Setup + 每个 RQ 一小节）
7 Discussion & Limitations
8 Related Work
9 Conclusion
```
- Atropos 最干脆：§2 就叫 "Challenges"，三个小节标题是 "Challenge 1: Complex Interface / Challenge 2: Stateful Environment / Challenge 3: Bug Oracles"，§3 Design 的小节逐一回应。
- AgentFuzz 把挑战写在 Intro 里（C1/C2/C3 三个问句），§4 "Overall Idea" 再写 "Challenges & Insights"，然后才进 Design。

**排法②"先研究、后工具"（PentestGPT、LLMSmith）**：先做一个实证研究/探索性研究，从研究结果里得出设计动机，再提工具。
- PentestGPT：§3 建基准 → §4 探索性研究（LLM 能做到什么、在哪失败）→ §5 方法 → §6 评测。
- LLMSmith：§3 设计 → §4 评测 → **§5 Empirical Study（单独一章的测量）**。

> 我们用**排法①**。我们的主干是方法，测量只是收获。排法②要拿一项完整研究当开头，那样会抢走方法的主干位置。

**几条结构上的共性**（都有出处）：
1. **真实漏洞例子放在第 1–2 页**：YuraScanner 的 Fig.1 是自己挖到的一个真实 XSS；AgentFuzz §2.2.1 "Real-world Example" 是一个真实 agent 的漏洞；NAUTILUS 单开 §3 "Running Example"（一个 CVE），Design 一节在这个例子上演示每个技术（Fig.5）。
2. **威胁模型放在 Background/Problem 里**，是一个小节（AgentFuzz §2.2.2），不单独成章。
3. **Design 第一小节一律是 Overview + 一张总图**，后面的小节和总图的方框一一对应。
4. **Implementation 都很短**（半页以内），有的直接并进 Evaluation 开头（NAUTILUS §5 "Implementation and Evaluation"；Black Widow §IV.A）。
5. **Evaluation 开头是一个统一的 Setup 小节**（数据集、baseline、指标、环境），后面每个 RQ 一节，不再重复写方法。
6. **Evaluation 后面常跟一节"结果分析"**（Black Widow §V "Analysis of Results"；Spider-Scents §6 "Analysis"），专门写：漏报了什么（"What we miss"）、别人漏了什么（"What others miss"）、误报怎么来的、可利用性、案例、协调披露。**这一节是把数字讲透的地方，审稿人很看重。**
7. **Related Work 多数放在后面**（Discussion 之后）。放前面的（AgentFuzz §3）通常是因为方法要先和前人划清界限。

### A.2 Introduction 的段落结构（逐段功能）

对照 AgentFuzz / YuraScanner / Black Widow / Spider-Scents 四篇 intro，段落功能高度一致：

| 段 | 功能 | 例子 |
|---|---|---|
| 1 | 这个系统是什么、为什么现在重要 | YuraScanner 第一句直接定义对象："Web application scanners represent the quintessence of black-box testing tools…"；**没有"安全很重要"之类的开场** |
| 2 | 现有方法缺在哪（按类别逐个点） | Spider-Scents 按 white/black/grey-box 三类，每类一段：做法 → 为什么不够 |
| 3 | 关键观察 / insight | Spider-Scents："our insight is to … by relaxing the requirement that…"；YuraScanner："we use LLMs based on the intuition that LLMs are trained on publicly available documents describing workflows" |
| 4 | 挑战（2–4 个，编号） | AgentFuzz C1–C3 每条是一个问句 + 一句为什么传统做法不行 |
| 5 | 我们的方法：一句话 + 几个阶段 | AgentFuzz："we design AgentFuzz with three main phases. In the first phase…" |
| 6 | 结果（带数字、带范围、点名系统） | YuraScanner 直接写 "four main takeaways. First, … 77% valid tasks (1,818 out of 2,361)…" |
| 7 | 贡献列表（3–5 条） | 每条一个动词开头：propose / implement / evaluate / disclose |

**审稿人第 2 页测试**（S&P 一审没有 rebuttal，读完前两页就会形成初步判断；来自 ieee-sp 技能）——读完第 2 页，审稿人必须能回答：攻击者是谁、能做什么？我们主张什么（一句话，带边界）？证据在哪一节？为什么现在做、难在哪？做得是否负责任（披露/伦理）？

### A.3 实验：别人怎么设计、遇到问题怎么解决

**A.3.1 RQ 怎么排**——看了 7 篇的 RQ 顺序：

| 论文 | RQ 顺序 |
|---|---|
| NAUTILUS | 检测能力 → 覆盖 → 消融 → 真实世界 |
| AgentFuzz | 检测 → **可利用性** → 对比 → 消融 |
| Witcher | 消融 → 检测 → 对比 |
| YuraScanner | 任务提取准确 → **任务执行成功率** → 攻击面覆盖 → **新攻击面的特征（深度）** → 漏洞检测 |
| PentestGPT | 性能 → 策略 → 消融 → 实用性 |
| Atropos | 找 bug → 覆盖 → 真实世界 → 消融 |

规律：**"能不能检出"放第一，"和别人比"、"每个部件有没有用"放中间，"真实世界"放最后**。YuraScanner 是唯一把智能体本身单独评的（能不能完成任务、失败在哪），和我们的阶段二最像。

**A.3.2 遇到的实验难题 → 他们怎么解决**（这部分对我们最有用）

| 难题 | 怎么解决 | 出处 |
|---|---|---|
| 漏洞检测里"真负例"没法定义，算不了 FPR | 误报率改用 FP/(FP+TP) | NAUTILUS |
| 和 baseline 比，差异可能来自载荷多少，而不是方法 | 所有工具换成同一套载荷字典，只比策略 | NAUTILUS |
| 想单独证明"探索能力"更强，但检测模块不同会混进来 | **直接复用 baseline 的检测引擎**，让对比只剩探索这一个变量 | YuraScanner（复用 Black Widow 的 XSS 引擎） |
| 同上 | 把自己找到的请求喂给对手工具（"BurpPlus"），隔离变量 | Witcher |
| 黑盒没有代码覆盖率 | 用"攻击面覆盖"：找到的表单数/URL 数，报**独有 / 共有**（A\B、A∩B、B\A） | YuraScanner、Black Widow |
| 智能体是否真的完成了多步任务 | **人工复核全部 2,361 个任务**，分成"完成/到倒数第二步/失败"，失败再按原因分类（状态不符 75%、动作错 25%） | YuraScanner Table II |
| 智能体到达的"深度"有没有价值 | 画"任务步数分布"+"新发现的攻击面在第几步出现" | YuraScanner Fig.7/8 |
| LLM 输出不确定 | temperature 设 0（AgentFuzz、GPTScan、KernelGPT）；多轮重复（ChatAFL 10 轮×24h） | — |
| **LLM 可能在训练时见过测试目标（数据污染）** | **测试目标只选模型训练截止之后出现的** | PentestGPT（靶机全选 2021 年后） |
| "检出"不等于"能利用" | 单开一个 RQ 证明检出的全都能利用 | AgentFuzz RQ2（34 个全确认可利用） |
| 漏报怎么交代 | 单开一节 "What we miss"，逐个说漏掉的原因 | Spider-Scents §6.3 |
| 同一漏洞报多次，数字虚高 | 写明去重规则并给理由（"同一行代码的多个字段算一个"） | Black Widow |
| 真实世界目标被质疑"本来就不安全" | 不选"设计上就不安全"的目标；不选多年不维护的项目 | Fuzzing SoK §5.5 |
| 漏洞数被质疑 | **被开发者拒绝的报告不能算漏洞**；只在维护者同意时申请 CVE | Fuzzing SoK §4.2（点名 SoFi 7 个浏览器漏洞全被拒） |
| 统计是否可靠 | ≥10 次重复；报效应量（Vargha-Delaney Â12）；用 bootstrap 而非只做 Mann-Whitney | Fuzzing SoK §5.6 |
| baseline 选得不当 | 除了 SOTA，也要和**简单方法**比（证明复杂方法确实必要） | Dos & Don'ts P6 |
| 样本有偏 | 交代样本怎么来、能代表什么 | Dos & Don'ts P1 |
| 标签不准 | 交代 ground truth 怎么确认的 | Dos & Don'ts P2 |
| 只在实验室里有效 | 加真实环境评测 | Dos & Don'ts P9 |

### A.5 句子怎么写：句与句之间的逻辑

你的要求是每句话都要和上一句有逻辑关系、没有废话、不做防御性写作。调研里能对上这个要求的写法有下面这些。

**1. 旧信息在前，新信息在后，一句接一句**（科学写作的经典原则，Gopen & Swan《The Science of Scientific Writing》）。每句的开头接上一句的结尾，读者就不会断线。Black Widow 的 intro 是很好的例子：

> Blackbox techniques … acquire such knowledge by interacting with running instances **with crawlers**. → **Crawlers** are a crucial component … that explore **the attack surface**. → If a crawler fails to cover **the attack surface** sufficiently, then **vulnerabilities may remain undetected**. → Unfortunately, having crawlers able to discover in-depth behaviors **is not sufficient to detect vulnerabilities**. → **The detection of vulnerabilities** often requires …

每句的主语都是上一句的落点（crawlers → attack surface → 漏洞没检出 → 光有爬虫不够 → 检测需要什么），整段就是一条链。

**2. 段落的第一句就是这一段的论点。** 只读每段第一句（topic sentence），整篇的论证也要连得起来（ieee-sp 技能的第 4 遍修订：只朗读主题句）。

**3. 用 LLM 必须先给 insight，说明 LLM 为什么在这里有效。** YuraScanner："we use LLMs based on the intuition that LLMs are trained on publicly available documents describing workflows"；AgentFuzz：类名和方法名"encompass rich natural language semantics that reflect their functional purpose"。审稿人不接受"用了 LLM 所以更好"，需要一句"这个问题里的信息以自然语言形式存在，所以 LLM 能读"。**我们的对应：MCP 工具的功能和依赖关系就写在自然语言描述里。**

**4. 每个主张都带边界 + 指向证据**（ieee-sp 技能的主张校准表）："X 在我们的 n 个目标上做到 Y（§6.2）"，不写 "effective"、"significant"、"devastating"。

**5. 反面例子（废话长什么样）**，这些在四大论文里也有，但正是我们要避免的：
- "Ensuring the security of web applications is of paramount importance for our modern society."（Black Widow 第一句：空洞的重要性开场）
- "However, sadly, existing studies reveal…"、"we are highly motivated to design…"、"it is definitely a non-trivial task"（AgentFuzz：情绪词、填充词）
- "one of the first …"（YuraScanner：既想说"首个"又加了保护，属于防御性写法）

**6. "不防御性写作"的正确做法**：限制和边界**集中写在一节 Limitations 里一次说清**，正文其他地方直接陈述（ieee-sp 技能："One Limitations subsection beats hedges scattered through every section"）。不做某件事时，给出技术理由（NAUTILUS："不做 X，因为它的判定标准无法统一建模"），不写"由于时间所限"。

**7. 时态与命名**：系统和方法用现在时（"the agent constructs…"），实验结果用过去时（"we found…"）；阶段编号、组件命名固定，便于审稿人在讨论里引用。

## B. 我们论文的整体框架（方案）

### B.0 全文主线（一句话）

> MCP 服务器把工具暴露给任何能连上端点的调用方；参数注入漏洞只能从这个端点黑盒地去找，而黑盒检测在 MCP 上有三个难点（**找哪个参数 / 到达目标工具 / 确认真触发**）；我们用三个技术逐一解决，并在已知漏洞集、对比实验和真实生态中验证。

全文的脊柱就是这三个难点：Intro 预告 → §3 展开 → §4 技术回应 → §6 消融证明。（已在 `论文方法讨论记录.md` §一 定下，这里只是把它落到章节上。）

### B.2 每章写什么

**§1 Introduction（7 段）**
1. MCP 是什么、部署形态（服务器在宿主机上，对外一个端点），它的工具会执行命令、读文件、发请求，参数由调用方提供。→ 引出：参数一旦流进这些操作，就是服务端注入。
2. 规模与危害：生态规模（用我们自己的测量数字）+ 已有 CVE 数量。→ 引出：需要自动化检测。
3. 现有做法为什么不够，按类别逐个说：白盒（要源码，市场上大量服务器拿不到/语言异构）、只看描述的扫描（不运行，判断不了真假）、现有黑盒工具（固定载荷 → 漏报；靠输出猜 → 误报）。
4. 三个难点（编号，各一句）：定位 / 到达 / 确认。
5. 我们的方法：一句话 + 三个阶段各一句（每句都写清"它回应哪个难点"）。
6. 结果：E1 召回/精确率；对比 mcpsnare/Corvus；真实生态扫描的数量与新漏洞；每个数都带分母。
7. 贡献列表（3–4 条，每条指向一节）+ 开源承诺。

**§2 Background and Threat Model**
- 2.1 MCP 协议：端点暴露了什么（`tools/list` 里的工具名、自然语言描述、参数 schema；`tools/call` 的返回）。**重点讲"黑盒视角下能看到什么、看不到什么"**——后面三个难点都从这里来。配 **图：MCP 交互与可观测面**。
- 2.2 威胁模型：按讨论记录 §一 的定义（普通部署、只知道端点的黑盒攻击者、危害落在宿主机）。能力和**非能力**都写（看不到源码、看不到服务端日志、不能插桩）。配 **图：威胁模型**。
- 2.3 Running Example：一个真实 CVE，**最好同时覆盖三个难点**（参数名看不出危险、要先调别的工具才能到达、回显本身不能证明执行了）。后面 §3、§4 都拿它演示。配 **图：真实漏洞示意**（放第 2 页以内）。

**§3 Challenges**（三个小节，各：现象 → 为什么显而易见的做法不行 → 用 running example 说明）
- C1 定位：没有源码，判断不了哪个参数会流进哪类危险操作；名字和类型不可靠。
- C2 到达：目标工具需要前置状态，所需的值只能从别的工具的返回里拿到，依赖关系只写在自然语言里。
- C3 确认：在外部看不到执行；回显不等于执行，正常功能不等于漏洞。
- 可选：每个难点配一个来自我们数据的数字（如"X% 的目标工具需要前置调用"）。这比空讲有力（NAUTILUS："82% 的漏洞需要多个 API 操作"）。

**§4 Design**
- 4.1 Overview：**总架构图**（黑盒膜 + 反馈闭环，已定）+ 一段走读，把三个阶段和三个难点对上。
- 4.2 基于语义的参数分类（← C1）：内容按讨论记录 §三。
- 4.3 智能体序列构建（← C2）：内容按讨论记录 §四；篇幅最大（约 1.5 页）。配 **图：running example 上的构建过程**。
- 4.4 执行确认（← C3）：内容按讨论记录 §五（探针、四个观测位置、差分、检测器×位置）。配 **表：漏洞类型 × 观测位置**。
- 每节第一段先给 insight（为什么这个技术在 MCP 上可行），再讲它保证什么性质；内部机制、阈值、prompt 进附录。

**§5 Implementation**：语言、代码规模、用的模型、怎么对接端点、开源。半栏以内。

**§6 Evaluation**
- 6.1 Setup：数据集（正 44 / 负 24，样本怎么来、ground truth 怎么确认）、baseline、指标口径（服务器级二元）、环境、LLM 设置与重复次数。**一次写完，后面不重复。**
- RQ1 有效性：在已知漏洞集上的召回/精确率（E1，已有）。附：漏报逐个归因（"What we miss"）。
- RQ2 对比：和 mcpsnare、Corvus 比，一张检出矩阵 + 独有/共有。
- RQ3 消融：三个技术各关一次，**每个消融对应一个难点**（语义 vs 关键词 / 智能体开 vs 关 / 差分开关 + 单位置 vs 多位置），报"有多少漏洞只有靠它才检出"。智能体那一项另报可达率、序列长度分布、失败分类（学 YuraScanner）。
- RQ4 真实生态：大规模扫描的规模、检出数、人工确认的新漏洞、披露与 CVE 状态；攻击面分布（测量作为收获，在这里出现）。
- （可选）6.x Analysis：漏报/误报来源、案例走读。如果篇幅紧，就并进各 RQ。

**§7 Discussion and Limitations**：逐条说边界，每条给技术理由（只做 5 类、黑盒看不到不回显也不出网的效应、LLM 不确定性的影响、测试床与真实部署的差别）；伦理（自建测试床、不打第三方线上服务、负责任披露）。S&P 注册时还要单独填 Ethics Considerations。

**§8 Related Work**：按类别分段：MCP/智能体安全（含白盒的 VIPER 等）→ 黑盒注入与 Web 扫描 → API/有状态测试 → LLM 辅助的安全测试。每段最后一句写清我们和这一类的区别轴。

**§9 Conclusion**：一段。

### B.4 调研暴露出来的、我们需要提前考虑的实验问题

1. **数据污染**：我们的正样本全是公开 CVE，审稿人可能问"LLM 是不是训练时见过这些漏洞"。可用的回应有三种：说明 LLM 只做参数分类和序列构建、不参与漏洞判定；标出训练截止之后才出现的 CVE 单独报结果（学 PentestGPT）；用真实生态里的新漏洞作为补充证据。
2. **简单 baseline**：除了 mcpsnare/Corvus，Dos & Don'ts 要求和"简单方法"比。我们的消融（关键词版、无智能体版）其实就是简单方法，写的时候点明这一层即可，不必另做（之前已定不做 LLM-only 稻草人）。
3. **重复次数**：Fuzzing SoK 建议 ≥10 轮。我们的单位成本高，至少要报多轮的方差，轮数到时再定。
4. **"设计上就危险"的目标**：Fuzzing SoK 明确说不要把"本来就该执行命令的工具"算作漏洞。这正是我们"本职功能 ≠ 漏洞"的判定，Setup 里要成文写出判定规则。
5. **真实世界新漏洞**：只报开发者确认的或我们人工确认可利用的；被拒的不报。

### B.5 待和你确认的几处（定了就开写）

1. **Challenges 单独成章（§3）还是写进 Intro？** 我建议单独成章：我们的脊柱是"难点 → 技术 → 消融"，单列一章最清楚（Atropos 的做法）。代价是多占约 0.5 页。
2. **测量放在哪？** 我建议作为 RQ4 放在 Evaluation 里，而不是像 LLMSmith 那样单开一章，因为测量是收获、不是主干。
3. **Running example 选哪个 CVE？** 需要从 44 个正样本里挑一个同时需要前置调用、而参数名看不出危险的。我可以先筛几个候选给你挑。
4. **RQ4 的数据什么时候有？** 大规模扫描还在跑（见 `deploy/cells/batch_run_log.md`），它决定 Intro 第 6 段和 RQ4 能写多少。

## C. 第一轮逐项讨论（2026-11-12 · 全部待定）

> 作者提出的四个问题。每项先写调研到的事实，再写可选做法和我的倾向。**都还没定。**

### C1. 用 CVE 统计证明"注入类危害真实存在、为什么检测这五类"

**作者想法**：收集所有 MCP 相关 CVE → 算注入类的占比 → 再算注入类里各类型的占比 → 以此说明为什么检测这五类。（思路来自一篇 REST API 论文，即 NAUTILUS。）

**NAUTILUS 是怎么写的**（USENIX'23，§2.2 "RESTful API Vulnerabilities"）：
- **位置**：放在 **Background 里的一个小节**，不单独成章。Intro 只抽出**一个数字**（"according to our empirical study of 609 vulnerabilities, 499 (82%) require multiple RESTful API operations"）来说明现有工具的缺口；贡献列表第一条就是这项研究（"We conduct an empirical study to comprehensively analyze the patterns of RESTful API vulnerabilities"）。
- **数据**：从 NVD 的 CVE 列表和 exploit-db 收集 609 个漏洞，人工阅读 CVE 描述、exploit、补丁来分析。
- **结构**：开头先说明这项研究要回答两个问题——RQ1 范围（漏洞分哪几类？）、RQ2 难点（触发漏洞和触发普通 bug 有什么不同？）。
- **分类**：按 CWE 分类，配一张图（Fig.2 漏洞类别分布）。结论：52.3% 是"用户输入处理不当"（各种注入），47.7% 是"资源管理不当"（越权、限流等）。
- **用来定范围时，给了两条理由**：① 占比最大（52.3%），且能导致命令注入、代码执行；② **另一类没法统一判定**（"difficult to model uniformly because it is difficult to define sensitive data in different contexts"）。不做的那类放进 Future Work。→ **只靠占比不够，还要配一条技术理由。**
- **同一项研究还用来推导难点**：总结出"检测漏洞"和"检测 bug"的三处不同（载荷、调用序列、判定方式），这三点正好对应它后面的方法。**一项研究同时管"范围"和"难点"两件事。**

**我们已有的基础**：10-28 那轮 CVE 分析（`scripts/` 采集标注流程）已经得出 1,075 条非恶意记录 → 581 条目标子集，**注入类约 67%，访问控制类约 25%**。另外，"需要多步"那一项当时被 LLM 标低了（只算了触发、没算确认），要重新人工标。

**放在哪**（可选）：
- (a) **Background 里的一个小节**（NAUTILUS 的做法）+ Intro 引一个数字 + 一张分布图。← 我倾向这个。
- (b) 单独一章 "Empirical Study"（类似 PentestGPT 的探索性研究）——篇幅太重，会抢方法的主干位置。
- (c) 只在 Intro 里提一句——太薄，审稿人看不到数据是怎么来的。

**可以顺带做的**：像 NAUTILUS 一样，让这项研究同时支撑难点，比如统计"利用这些 CVE 需要前置调用的比例"→ 撑 C2 到达难点；"多少漏洞的效应不回显"→ 撑 C3 确认难点。这样研究和方法就连起来了，不是一张孤立的统计图。

**要注意**：五类里的"参数注入"和"代码注入"在 CWE 上可能和命令注入分不开，分类口径要先定好；占比只用来交代范围，配合技术理由（"这五类的效应都能从端点外部观测到"之类）一起写，不单凭占比高低下结论（呼应作者"不用占比判断值不值得做"的原则）。

### C2. 贡献列表写不写？数据集怎么提？挑战拆不拆？

**贡献列表**：几乎都写。18 篇里 **16 篇有明确的贡献列表**，用 "In summary, we make the following contributions:" 引出，3–5 条，每条一个动词开头（propose / implement / evaluate / conduct / release）。S&P 审稿人会用它来对照每条主张的证据在哪。→ **要写**，具体几条、写什么，等方法和实验定了再回来写。

**数据集怎么提**（别人的写法）：
- AgentFuzz：贡献列表之后单独一句 "We publicly release the source code of AgentFuzz, along with the datasets and baselines used for evaluation"。
- NAUTILUS：列表之后一句 "To facilitate future research, we will release the source code…"。
- 把数据集**作为一条贡献**写进列表的情况：当数据集本身是可复用的基准时（可部署、可复现、带利用脚本）。作者计划的"Docker 一键部署 + 利用脚本"正符合这个标准（Fuzzing SoK §5.1 也强调用 Docker 等环境封装来保证可复现）。
- 正文只需一条贡献加一句开源声明；Docker、脚本这些细节放到 artifact 和附录。

→ 可选：(a) 数据集单列一条贡献（"a reproducible benchmark of N vulnerable MCP servers with deployable environments and exploits"）；(b) 只在列表后写一句开源。我倾向 (a)，因为它确实是可复用的基准；"首个"之类的说法不写（novelty 先不定）。

**挑战拆不拆**——统计结果：
- **编号拆开写的占绝大多数**：Witcher（4 条）、AgentFuzz（C1–C3）、Atropos（Challenge 1–3）、Black Widow（3 条）、NAUTILUS（3 条理由）、ChatAFL（A/B/C）。没见到把挑战写成一整段不拆的工具论文。
- **写在哪里分两种，大约各一半**：
  - 只写在 Intro 里（Witcher、NAUTILUS、KernelGPT）：每条一两句。
  - **Intro 简述 + 单独一节展开**（Atropos §2、Black Widow §II、Spider-Scents §3 "Roadblocks"、Snipuzz §3 Motivation、AgentFuzz Intro + §4.1）：Intro 每条一句，专门那一节每条一段，并配例子。
- 规律：挑战越需要例子才讲得清，越倾向单独成节。我们的三个难点（定位/到达/确认）都需要 running example 才讲得清，所以倾向"Intro 简述 + 单独成节"。待定。

**怎么引**（惯例）：
- 格式：IEEE 数字编号 `[12]`，用 IEEEtran.bst 自动生成（我们的模板已配好）。多篇一起引写成 `[23, 32, 46]`。
- **工具第一次出现时写名字加编号**："ZAP [14]"、"LLMSmith [49]"。句子主语用工具名或作者，不用编号（写 "Witcher [x] does…"，不写 "[x] does…"）。
- **非论文来源也进参考文献**：漏洞赏金报告、行业调查、OWASP、协议规范、GitHub 项目（Black Widow 的 "$6.5 million [16]"、NAUTILUS 的 Salt Security 调查 [13]）。对我们来说，MCP 官方规范、mcpsnare（无论文）、市场网站都按这种方式引。
- CVE 编号一般直接写在正文里（"CVE-2021-21389"），NVD 作为数据来源引一次即可。
- 有正式发表版本的，引正式版，不引 arXiv（ieee-sp 技能：用 dblp 核对会议和年份）。
- 双盲期间引自己以前的工作要用第三人称。

**相关工作那一节怎么写**：
- 按类别分段，每段用一个加粗的短标题开头（AgentFuzz："Vulnerability Detection of LLM-based Agents." / "Taint-Style Vulnerability Detection."）。
- 每段的结构：这一类做了什么 → 它的局限或和我们的区别。最近的那个竞品单独点名对比（Atropos："Closest to our work is WITCHER… In contrast, ATROPOS…"）。
- S&P 要求区别必须是**安全上的区别**（能对付更强的攻击者、需要更弱的前提、覆盖一整类），而不只是"更快"（ieee-sp 技能）。
- S&P 审稿人会检查的覆盖面：近 3 年四大里的同类工作、被测对象所在领域（MCP/智能体）、已有的 SoK、测量类工作。
- 位置：多数放在后面（Discussion 之后）；放前面的（AgentFuzz §3）是为了先用前人的局限来引出动机。

**我们大概需要的几类文献**（只是初步）：MCP 协议与生态、MCP/智能体安全（白盒的 VIPER 等、描述层面的检测、提示注入）、黑盒注入与 Web 扫描、有状态 API 测试、用 LLM 做安全测试、评测方法论（Fuzzing SoK 等）。

### C4. 对比实验：baseline 不搭怎么办？有没有不和 baseline 比的？

**别人的 baseline 选法可以分四种**：

| 情况 | 做法 | 例子 |
|---|---|---|
| ① 同领域有成熟工具 | 直接比，比好几个 | Black Widow（7 个扫描器）、NAUTILUS、Witcher、Atropos、ChatAFL、KernelGPT |
| ② 同领域只有一个，而且很弱、路线也不同 | **照样比**，它的弱正好说明缺口；再把自己的消融变体当作额外的 baseline | **AgentFuzz**：只和 LLMSmith 比（对方是静态分析，精确率 2.9% vs 100%），主表里同时列 AgentFuzz-NoGen 等变体 |
| ③ 同领域没有能直接比的 | **借用相邻领域的工具**，必要时改造或重新实现；并用一句话说明为什么别的工具不能当 baseline | **Snipuzz**：改用通用网络 fuzzer（BooFuzz、Doona、Nemesys），重新实现了 IoTFuzzer；明说灰盒工具"infeasible and unfair to regard as baselines for black-box schemes"。NAUTILUS 把 REST 测试工具改造成能发攻击载荷 |
| ④ 加"简单策略"作为 baseline | 用朴素做法证明复杂方法确实必要 | **YuraScanner**：除了 Black Widow，还和 BFS、随机 BFS 两种朴素导航比；PentestGPT：和直接用 GPT-3.5/4 比 |

**确实有不做端到端对比的**：**LLMSmith（CCS'24）**。它是这个方向的开创者，没有可比的工具，所以只在**组件层面**比（自己的调用链提取 vs 通用静态分析工具 PyCG），其余用测量和真实漏洞利用来支撑。Atropos 还另做了一张表，**和白盒静态分析工具**在真实漏洞上比（Table 2），这样跨路线的对比就不和主对比混在一起。

**审稿人的尺子**：
- Fuzzing SoK §5.3：要和"所在领域的 SOTA"比；有可拆的设计时，用消融单独评每个部件。
- Dos & Don'ts P6：要和**简单方法**比，证明复杂方法确实必要。
- 规律：**完全没有对比，只在"开创性 + 组件级对比 + 强真实世界结果"同时成立时才能被接受**。我们已经不能说"首个黑盒"，所以完全不比风险很高。

**对我们的可选组合**（待讨论；先想清楚"不搭"具体指什么——是覆盖类别不同、确认方式太弱，还是部署方式不同）：
- (a) **保留 mcpsnare + Corvus 作为端到端对比**：它们是唯一能在同样条件下（黑盒、走端点）和我们比的。弱不是问题，AgentFuzz 只有一个弱 baseline 也被接受了；它们漏检、误报多，正好说明缺口。
- (b) **把消融变体也放进主对比表**（AgentFuzz、PentestGPT 的做法）：关键词版、无智能体版、只用带外确认版，各代表一种"朴素做法"。这同时满足"和简单方法比"的要求，而且不是稻草人，因为每个都对应一种现实中会用的做法。
- (c) **单独一张跨路线的对比表**（Atropos Table 2 的做法）：在有源码的子集上和白盒工具比（如 VIPER-MCP），或只在描述层面检测的工具比。明说它们的前提不同，只作参考，不和主对比混在一起。
- (d) 组件级对比（LLMSmith 的做法）：比如我们的参数分类 vs 关键词规则，我们的序列构建 vs 一次性规划。这其实已经是消融。

我的倾向是 (a)+(b) 为主，(c) 视情况加。(a) 原来就定了，"不搭"的感觉可以用 (b)(c) 补足，不需要推翻 (a)。具体等你说清"不搭"指什么再定。

## D. 别人的 Introduction 写了什么（逐段拆解 · 2026-11-12）

> 读了 7 篇的引言全文，逐段标出"这段在做什么"。原文句子供对照。**只是调研，我们的引言怎么写仍待定。**

### D.1 逐篇拆解

**LLMSmith（CCS'24，LLM 应用的 RCE；和我们的背景最像）**
1. LLM 能力强（代码生成、数据分析、程序修复）→ 开发者纷纷把 LLM 集成进应用 → 为了方便集成，出现了 LangChain 等框架，GitHub 上上千星 → 开发者通过调用框架 API 来构建应用。**最后一句转折**："However, these frameworks may also have potential vulnerabilities, influencing the security of apps built on these frameworks."
2. 已有工作发现过 SQL 注入（攻击者通过提示注入远程利用）→ 我们发现更严重的 RCE → 这类攻击成立需要两个条件：**(1) LLM 的回答不可控**，攻击者能用构造的提示操纵输出；**(2) 框架执行了不可信的代码**，即 LLM 生成的代码没经检查就被执行。→ 目前没有系统研究。
3. Challenges：两条。
4. Our Approach：三步，每步带节号。
5. 结果（数字）。
6. 贡献：三条，每条一个加粗短标题加两三句解释。

**AgentFuzz（USENIX'25，LLM 智能体的污点类漏洞）**
1. LLM 进步 → 开发者用它构建智能体 → 智能体的两种部署形态（本地桌面、远程网站）→ 智能体执行代码、处理敏感数据，平台上用户上百万 → 所以安全重要。
2. 已有研究表明智能体易受提示注入 → 污点类漏洞最关键 → **成因**："developers' over-reliance on LLM outputs and failure to sanitize harmful content before passing it to security-sensitive operations" → 已有检测方法（LLMSmith 的静态分析）误报、漏报都高。
3. 所以要做检测 → 定向 fuzzing 适合（因为漏洞只在特定危险操作处触发）→ 但迁移到智能体上不容易。
4. 三个挑战 C1–C3，每个一个问句加原因。
5. 提出 AgentFuzz + 三条 insight（逐一对应 C1–C3）+ 三个阶段。
6. 结果：20 个智能体、34 个 0-day、精确率 100%、23 个 CVE、负责任披露。
7. 贡献三条。

**NAUTILUS（USENIX'23，REST API 漏洞检测）**
1. REST 流行（Google、微软在用）→ 成了攻击入口 → 行业调查：91% 的受访者在 2021 年遇到过 API 安全事件 → 所以早期检测重要。
2. 渗透测试是常用做法 → 自动化工具比人工稳定 → 现有两个工具 ZAP、w3af 用预设载荷逐个测 API → **但只能测单个操作的漏洞**；而**我们对 609 个漏洞的实证研究**显示 82% 需要多个操作（OWASP、Rapid7 也印证）→ 所以需要能生成操作序列的技术。
3. 已有序列生成工具（RESTler 等）不适合找漏洞，三条原因（序列不针对漏洞 / 规范信息不够 / 缺载荷和判定）→ "a huge research gap"。
4. 提出 NAUTILUS：核心设计（注解）+ 两个阶段。
5. 结果（覆盖率提升范围、真实世界 23 个漏洞、厂商确认、CVE）。
6. 贡献五条（第一条就是实证研究）+ 开源。

**Witcher（S&P'23，Web 注入漏洞）**
1. Web 漏洞不减 → 后果严重（开发者、公司、用户三方）→ 数量多、种类杂，需要自动化。
2. 已有工作分白盒、黑盒、灰盒三类，**各一段**，每段写"它怎么做 → 为什么不够 → 后果"：白盒要源码、绑定语言；黑盒用硬编码载荷 → 漏报，靠输出推断 → 误报，并举 HTTP 500 的具体例子；灰盒只支持单一语言、闭源、慢。
3. 提出 Witcher：一句 idea。
4. **先给挑战的共同根源**："the challenges … arise because the web application code … is not the entire execution object"，然后列四个挑战（加粗句子做小标题）。
5. "Witcher is designed to tackle the prior four challenges" + 实现范围（6 种语言）+ 评估设计 + 结果。
6. 贡献。

**YuraScanner（NDSS'25）**：①直接定义对象（Web 扫描器）和它的短板（不懂多步流程）→ ②已有改进（基于模型的方法、LLM 浏览助手）各自为什么不行 → ③提出方法 + 用 LLM 的 intuition → ④评估设计 → ⑤"four main takeaways"逐条带数字 → ⑥贡献五条。

## E. 序列构建(stage 2)怎么证明有用 —— 换口径(2026-11-12)

> 背景:44 CVE 注入点里真需要前置序列的只有 ≈3 个(见 `data/groundtruth/前置序列核实.md`),CVE 集偏浅。作者定:**不以漏洞数作统计单位**。

### E.1 换两样东西
1. **统计单位:从"漏洞"换成"工具/目标的可达性"。** 到达是每个工具都有的属性,和它有没有漏洞无关 → 在**所有工具**上测,而不是在漏洞上测。
2. **数据集:从 44 CVE 集换成大规模无偏的工具总体**(每台扫描服务器的每个工具)。CVE 集偏浅、N 小;工具总体不偏、N 大(成百上千),还不需要漏洞标签。

### E.2 "到达"是黑盒可观测的
- **reached(到达)= 服务器返回了成功的工具结果(非协议/校验错误)**;**unreached = 建不出被接受的调用**。不需要源码。日志里已有 reached/unreached 状态。
- 这个粒度对 stage 2 正好:stage 2 管"把工具调通到执行",是否命中 sink 是 stage 3(oracle)的事。

### E.3 指标(都不以漏洞计)
1. **可达率(主指标)**:目标工具里有多少拿到"被接受且执行"的调用。**智能体开 vs 关**。现有:开=未达率 3.4%;关掉的数要跑。
2. **序列必要性**:在能到达的工具里,有多少**单独一次调不通、必须先调别的工具**才调通 → 用**单次回放**得到(单次 vs 智能体序列)。这是支撑"到达难"挑战的核心数,纯可达性、无漏洞。
3. **序列统计**:长度分布、用到几个不同的"生产者"工具、深度。
4. **失败归因分桶**:unreached 的工具为什么没到(schema 拒/缺不透明值/状态没建起/预算耗尽)。
5. **测量有效性**:可达性让"干净"与"根本没到"分得开(unreached≠clean),使召回/精确率有意义。

### E.4 消融 = 只做"单次调用"对比(2026-11-12 作者定)
- **一条对照臂:单次调用(agent off,直接单调目标工具一次,不做任何前置调用)。** 不做一次性规划那条臂。
- 对比:**完整智能体(建序列)vs 单次调用**,看可达率各是多少。差值 = 需要前置序列才能到达的工具。
- 单次调用臂保留参数生成(照样填必填参数),这样差值只归因于"序列构建"本身;凡是必须从前置调用返回里取的不透明值,单次调用自然填不出来——这正是要暴露的。

### E.5 数据集 = 现有服务器,不等大规模集(2026-11-12 作者定)
- 大规模集还没出来,**不用**。就在现有已部署服务器(44 正 + 可选 24 负)的**全部工具**上测可达性(可达性与漏洞无关,N 比 CVE 点大得多,现有 44 正上已有 2513 个目标)。
- 大规模集将来出来可再补一版无偏的数。

### E.6 待定 / 要做
- **"reached" 判定口径要先成文钉死**:什么算"工具真的执行了"、什么算"被拒/没到"(MCP 响应的 isError、schema 校验拒绝、工具内部报错怎么归)。这个不定清楚,数就不准。
- **要加一个"单次调用模式"**:直接单调目标工具、填参数、不做前置。然后在同一批服务器上把"完整智能体"和"单次调用"都跑一遍,按每个工具/目标比可达率。
- 完整智能体那一臂的 agent-on 可达数据,现有定型日志里已有(未达率 3.4%),但为口径一致,最好两臂用同代码同条件重跑。

### E.7 ✅ stage 2 可达性数据(定稿·冻结快照口径·2026-11-12)

> 口径:**分母 = 486**(定型那次阶段一分类器判定为"含可注入参数"的工具目标,**冻结快照**)。

### E.8 ✅ 引言·三难点与两观察(定稿 2026-11-12)

> 定稿=逐段逻辑链,不是成稿句子。写作时句与句须因果相扣(见记忆 feedback-writing-causal-chain)。

**三个难点(§3,引言第5段预告)** —— 共同根源:端点只给工具名/自然语言描述/参数结构,服务器实现、工具间依赖、服务端执行都看不见。三难点都从此来。每个难点三步写:难在哪 → 为什么在黑盒MCP下难 → 朴素做法为什么不行(点"朴素策略"的失败,**不点名具体工具**,工具批评在引言第4段缺口段+相关工作)。抽象高度一致,三连=该打哪/够得着吗/是不是真漏洞,全停在"为什么难",怎么解留给§4。

- **难点一 定位(该打哪个参数)**:要知道哪个参数的值会流进危险操作;端点只给参数结构(形状)不给去向,看不到实现就看不到数据流;朴素做法=按参数名关键词猜,但名字与真实去向常对不上(value被拼进命令、path只是逻辑id),既漏又误。
- **难点二 到达(够不够得着)**:要把攻击真送到危险操作;有些危险操作只有服务器被先前调用带入某状态后才执行得到,而前置依赖只写在自然语言描述里;朴素做法=每个工具单独调一次,这类工具单调到不了被漏掉。**只点存在性,不给普遍程度的数**(数留后面测量章)。
- **难点三 判定(是不是真漏洞)**:即便攻击送达,也要判断是否真触发了漏洞;检测者在端点外部看不到服务端内部执行,唯一能依据的是响应;朴素做法=照响应判,但响应不能直接说明漏洞是否被触发,容易误判。**抽象到此为止,不提回显/本职功能/差分/多位置**(全是解法,进§4/§5)。

**两个观察(§引言第6段,insight单独成段)** —— 每个=一个关于MCP/注入的**事实**,方法从事实推出(推论不写进观察本身)。

- **观察一(事实)**:MCP工具描述是用自然语言写给模型读的——用途、参数含义、调用前提都在里面,因为MCP靠模型读懂描述才能正确调用工具。→ 推出:定位/到达所需信息没藏在源码里、摆在描述中,能读懂描述的读者(LLM)就能还原。**对应难点一+难点二。**
- **观察二(事实)**:服务端注入的本质是服务器执行了一个真实的动作(运行命令/读文件/发请求/求值),不只是响应内容变了;真实动作会在**响应之外**留下后果,单纯返回文本不会。→ 推出:真漏洞可靠动作的后果来确认,不必从响应推断(用什么后果、怎么排干扰=§4/§5)。**对应难点三。**
- 收尾句把观察引到方法:"基于这两个观察,我们设计了三个阶段"——观察一落阶段一(定位)+阶段二(到达),观察二落阶段三(判定)。

**映射**:观察一→难点一/二→阶段一/二;观察二→难点三→阶段三。三难点、两观察、三阶段三处同序同词。

**纠偏记录**:观察二曾写成"我们可以让漏洞自证"(=方法)被否;改为"注入本来就是会留后果的真实动作"(=事实)。难点三曾写成回显/本职/差分(太具体)被否;改为抽象"判定是否真漏洞难"。
