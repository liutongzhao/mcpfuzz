# 代码注入（code_injection）检测与判定设计

> 把「第二阶段」里一直占位的 **代码注入（CWE-94，语言解释器 / 模板 / eval 边界）** 正式纳入检测，作为继
> 命令注入 / 参数注入 / 路径穿越 / SSRF 之后的第 5 个启用类别。
>
> 关联：`docs/漏洞类型与检测手段.md`（§6 占位升级为本文件）、`docs/判定方法论.md`（五原则、探针模型、
> 证据阶梯）、`docs/Sink推断模块设计.md`（declared_domain 的产出位）、`docs/载荷合成模块设计.md`（电池格式）。
>
> **设计前提（用户已拍板）**：
> 1. 收这一类的理由是**覆盖一致性**——既然收了更少见的参数注入（17 条 CVE），就该收更常见、同属注入家族的
>    代码注入（36 条 CVE / 可测子集 20 条），否则论文里无法自圆其说。不是用占比高低论证研究价值。
> 2. 判定走**严版**：确认漏洞 = 证明发生求值（L1）**且**证明求值越过了该参数声明的用途（L2）。
> 3. 「声明用途」**不枚举代码类关键词**（枚举不全），由 **sink 推断的 LLM 产出、强制引用描述原文**，且 LLM
>    只给“声明用途”这个基线，**不碰“是不是漏洞”的最终裁决**——裁决落在可观测的 L2 越域上。

---

## 1. 这是什么漏洞，和已有四类怎么区分

**定义**：不可信输入流进一个“代码/表达式求值器”，被当代码执行而非数据。

| | 命令注入 CWE-78 | **代码注入 CWE-94** |
|---|---|---|
| 输入流向 | 操作系统 shell | **进程内的语言解释器 / 模板引擎** |
| 典型 sink | `exec`/`system`/`subprocess(shell=True)` | `eval`/`exec`/`compile`、`Function()`/`vm`、SymPy `parse_expr`、Jinja2/Handlebars/EL 模板 |
| 执行环境 | 新起 shell 进程 | 服务自己的进程、自己的语言运行时 |

**模板注入（SSTI）是其子型**：输入拼进模板串，引擎把 `{{...}}` / `${...}` / `#{...}` 当表达式求值。

**为什么 MCP 多发**：大量 MCP 工具是“计算器 / 跑公式 / 按 spec 渲染图表 / 执行脚本 / REPL”，天然把参数喂给求值器。
数据集里 qwed-mcp（SymPy `parse_expr`）、fermat-mcp、mcp-vegalite-server（`visualize_data` eval）、Jij-MCP-Server
（PythonREPL）、mcp-contextforge-gateway（SSTI）均属此类。

**危害**：一旦确认 = 服务进程内任意代码执行（RCE）。放到威胁模型（容器即宿主 + agent 中介）：读进程内密钥 /
网关凭据、读写容器文件、任意网络请求、横向打穿同容器其它 MCP。常比命令注入更危险——在进程内、用服务自身运行时，
**不需要 shell**，能绕过“禁 shell / 过滤 shell 元字符”的环境。

---

## 2. 核心判定原则：求值回显 + 越域（两步，缺一不可）

沿用工具招牌逻辑（`executor.observe_inband`：**签名不在我发出的载荷里、却出现在响应里 = 服务端算出来的**）。

- **L1 证明发生了求值**：发一个算术/字符串 canary，响应里出现它的**计算结果**（我没有把结果字面发出去）→
  只能是服务端求值产生。随机操作数 + 差分杜绝“恰好撞上固定数字”。
- **L2 证明求值越过了参数声明的用途**：实测求值**够到了声明用途根本不需要的能力**（导入模块 / 文件 / 网络 /
  访问任意对象图 / 通用字符串与反射运算）。

**只有 L1 且 L2 同时成立才算漏洞。** 只满足 L1、而该参数本身声明用途就是“求值/执行代码”（计算器、REPL）→
判为 **dangerous-by-design**（像 send_command、git_clone 一样单独归置，不计入 CVE 类漏洞；论文里塌成“未报漏洞”）。

> 这一类是“漏洞 vs 本职功能”判定最尖锐的类别：对前四类，意图闸门是加分项；对代码注入，它是**必需项**。

## 3. 载荷怎么发（新增 `_code_battery()`，CODE 类）

黑盒不知道后端语言/引擎，故发一个**引擎族 × 分层通道的矩阵**，哪条回显出结果就暴露哪种引擎——与命令注入发全套
`_CI_CONTEXTS` 同一思路，**通用静态模板，不针对任何服务器**。排序遵守现有约定：不出网、无破坏的在前，`sleep`/
带外/写文件靠后，按权重分预算取 top-N。

**求值 canary 的关键设计**：每次用**随机操作数**（如两个随机 4 位数 `{A} {B}`），预期结果是我没发出去的 6–8 位
积，带 `{TOKEN}` 前缀绑定溯源。响应里出现 `{TOKEN}<积>` → 求值成立。`control` 配一个同形但不求值的对照值。

| 层 | 通道 | 载荷形态（代表，`{A}{B}` 随机、`{TOKEN}` 绑定、`{PROD}`=A×B） | 作用 | 证据级 |
|---|---|---|---|---|
| **L1 求值回显**（最先、无破坏、网络无关） | inband | 各引擎表达式语法并发：裸 `{A}*{B}`、`${{A}*{B}}`、`{{{A}*{B}}}`、`#{{A}*{B}}`、`<%= {A}*{B} %>`、`${ {A}*{B} }`，`expect=["{TOKEN}{PROD}"]` | 证明**发生求值** + 指认引擎 | ◎（结果不在载荷里） |
| **L2 越域能力**（证明是“代码”不止“算数”） | inband | 只有通用代码/模板引擎能做、纯数学算子做不到的**非算术运算**产出可识别 canary：字符串构造/拼接、长度、类型/对象反射得到 `{TOKEN}` 的可预测变形值；`expect` 为该变形值 | 把“算术求值”升级为“代码注入”——**L2 证据** | ◎（变形值不在载荷里） |
| **L3 解释器报错**（弱证据） | inband 错误指纹 | 故意语法错的表达式 → 特定解释器 traceback | 仅作**疑似**旁证，不单独定案 | △ |
| **L4 时间盲判**（会拖慢，靠后） | timing | 语言级延时表达式 + `control`=零延时 | 无回显时的盲态确认 | ○（N 次重复 + 阈值去抖） |
| **L5 越域影响**（默认**关**，仅 E4 危害案例用） | oob / cross_tool | 够到环境变量 / 外带回连 / 落地 canary 文件 | 危害闭环演示，走负责任披露 | 检测**不依赖它**，避免 DoS 与伦理问题 |

说明：
- **L1 开箱即用**：求值结果不在载荷里，现有 `observe_inband` 的“签名非载荷子串 → 铁证确认”逻辑直接判成立，无需新
  判定代码；主要新增量是 **L2 越域探针** 与 **意图闸门**。
- L2 的“越域运算”是**通用语言能力探测**（字符串/反射/对象图），不是“针对某服务的利用链”；真正的完整 RCE 链属于
  L5 / E4，不进检测必经路径。
- `reflection_safe`：L1/L2 的 `expect` 都是**计算产物**、不等于所发字面 → 反射回显不会误命中（与 CI 的
  `token1681` 同理）。

## 4. 怎么判参数的“声明用途”——复用 sink 推断 LLM，强制引用原文

**判断者 = 现有 `sink/llm.py` 那一次调用**，不新增判断环节。它现在已经：喂进**该 MCP 自身声明的东西**（工具名 +
description + 每参数 path/type/required/enum/description），并被强制**先说工具干什么、每个标签必须引用
description/schema 原话，引不出原话就不许打标签**。

**扩一点**：对被标为 `code_injection` 的参数，同一次调用额外产出
```
"declared_domain": "<一句话：该参数/工具自称的用途>",
"domain_evidence": "<从 description 或 schema 引用的原话>"
```
**复用它最硬的纪律——必须引用原文**：描述里引不出任何说明用途的原话 → `declared_domain` 留空 → 无法减去
dangerous-by-design → 保守按“未知域”处理（宁可少报）。

**为什么这样用 LLM 站得住**：我们没让 LLM 判“是不是漏洞”（会循环、也软）。只让它做**阅读理解**——把工具自己声明的
用途、带引文复述出来；真正那刀“是不是漏洞”落在**机械可观测的 L2 越域**上。分工三条保障：
1. **引文锚定**：说不出原话就不认，杜绝脑补用途。
2. **只做减法**：声明域判错，最坏只是把 finding 在“漏洞 ↔ dangerous-by-design”间挪一下，不会凭空造漏洞；边界
   情况 E3.3 人工核实兜底。
3. **按工具缓存**：一次跑内确定；跨轮 LLM 抖动按刚性要求多轮跑报方差。

> `declared_domain` 不是 code/data 的二分标签，而是“LLM 概括的声明计算域 + 引文”。判定不匹配任何关键词表。

## 5. 判定裁决（五态 + 意图闸门）

| 结论 | 触发条件 | 计入准确率表 |
|---|---|---|
| **CONFIRMED（漏洞）** | L1 求值成立 **且** L2 实测能力越过 `declared_domain`（含：声明域为空/未知时，L2 越域即判漏洞） | 是，正类 |
| **dangerous-by-design** | L1 成立，但实测能力都落在 `declared_domain` 内（计算器算数、REPL 执行代码） | 否（单独归置，论文塌成“未报漏洞”） |
| **SUSPECTED** | 仅 L3 解释器报错，或 L1 成立但 L2 未够到、越域存疑 | 消融内部用，不进正文 |
| **NOT_TRIGGERED** | 载荷被 schema 校验挡下（未真正送达求值器） | 按原因分桶（校验拒） |
| **LIKELY_CLEAN** | 送达但无任何求值迹象、无报错指纹 | 负向 |
| **SKIPPED** | 环境测不了（依赖缺失等） | 不计干净、不计漏洞 |

**严版的代价（如实写进 Limitations）**：声明用途本就很宽（什么都能干）的工具，会保守落到 dangerous-by-design、
宁可少报。符合口径“只报人工验证为真的正例”，边界交 E3.3 人工核实兜底，不靠工具硬判。

## 6. 接到现有架构的改动点

| 文件 | 改动 |
|---|---|
| `sink/types.py` | `PHASE1_CLASSES` 增加 `CODE`（`sink/rules.py`、`sink/llm.py` 已认得 CODE，无需改分类） |
| `sink/llm.py` | SYSTEM/输出 schema 增 `declared_domain` + `domain_evidence`（仅对 code_injection 参数要求），沿用“必须引用原文”纪律 |
| `sink/types.py`（ParamSinkPrior） | 透传 `declared_domain`（供 executor 意图闸门读取） |
| `payload/batteries.py` | 新增 `_code_battery()`，注册进 `_BATTERIES[CODE]`（L1/L2/L3/L4；L5 默认关，开关控制） |
| `oracle/fingerprint.py` | `_PATTERNS` 增 `CODE` 组：各解释器 traceback 通用正则（弱证据，不单独定案；参照 AI/SSRF 的“通用、不针对服务、不枚举应用层措辞”约束） |
| `orchestrator/executor.py` | CODE 的 L1 走现有 `observe_inband`（结果非载荷子串 → 求值成立）；**新增意图闸门**：confirmed 前比对 `declared_domain`，越域才 CONFIRMED，域内降级为 dangerous-by-design |
| `report.py` / 五态 | 新增 dangerous-by-design 归置（与现有 SSRF 信任边界 / 命令执行本职功能同一出口），确保不混进漏洞计数 |

L1 复用度极高，净新增主要是 **L2 越域探针 + declared_domain 产出位 + 意图闸门**三处。

## 7. 对评估（RQ1/消融）的影响

- 代码注入成为准确率表里的**第 5 类**，正/负样本与前四类同口径（服务器级二元对外；漏洞级进消融）。
- 消融“求值回显 + 差分骨架 oracle”这一行，**代码注入是它最直接的实例**（L1 回显 = 该组件的核心增益），和命令注入
  一起作为“执行确认 vs 输入回显”区分能力的证据。
- dangerous-by-design 的降级数**不计入 FP、也不计入 TP**，单列“意图层正确降级”计数，作为“判定语义正确性”的佐证
  （与 send_command、git_clone 的降级同一张表）。
- 刚性要求照旧：多轮跑报方差（LLM 产 declared_domain 有抖动）、pin 版本 + env.lock + 快照日期、原始输出归档。

## 9. 实现状态（2026-11-05，已落地）

检测能力**已实现并离线验证通过**（改动点见 §6）。相比本文前面的设计稿，实现阶段用户敲定了两处口径，记录如下以保文档与代码一致：

**（a）采用口径 B：不自动降级 dangerous-by-design。** §5 原设计让工具据 `declared_domain` 自动把"声明用途即执行代码"的参数降级为 dangerous-by-design；但数据集里的代码注入正样本（pptr-mcp `execute`、Jij `jm_check.code`）正属此类，自动降级会让工具对自己的 CVE 漏报。故定：**L1+L2 命中即 CONFIRMED，`declared_domain` 只作 finding 附注供人工判定**，dangerous-by-design 的归置交报告层/人工（符合"只报人工验证为真"口径）。工具不新增 dangerous-by-design 状态。

**（b）L1/L2 以载荷形态操作化，与 §3 表格的分层口径不同。** §3 把所有引擎语法（裸 / `${}` / `{{}}` / `#{}` / `<%=%>`）都归 L1。实现改为：
- **L1 = 裸算术**（`A*B`、`A * B`）：证明发生求值，但可能只是受限计算器 → 单独**仅判 SUSPECTED**。
- **L2 = 参数被当"代码/模板结构"处理**：①模板 delimiter 族（`{{}}`/`${}`/`<%=%>`/`#{}`，引擎须识别分隔符才求值＝SSTI/模板注入）；②函数调用族（`ord()`/`charCodeAt()`/`length`，纯算术解析器做不到）→ 命中即 **CONFIRMED**。
- 理由：模板引擎对 `{{A*B}}` 求值本身即越域（对非模板工具），且纯算术计算器会在 `{{`/`ord(` 处报错不回显——以载荷形态区分"计算器"与"代码/模板引擎"，比依赖 `declared_domain` 文本比对更机械、更利于模板注入召回。
- 判定流转（`executor._attack_param`）：L2 inband 命中（且非反射）→ 立即 CONFIRMED（附 `declared_domain`）；L1 命中先记录不定案、继续找 L2；全程仅 L1 → SUSPECTED；仅 L3 解释器报错指纹 → SUSPECTED；timing 通道（`__import__("time").sleep`）命中 → CONFIRMED（RCE 级）。
- 随机操作数（每次 synthesize 重取 4 位 A/B）+ 期望签名＝算出的积/变换值（不在载荷里）→ 反射免疫、抗巧合撞数。

**离线单测**（`selftest_code.py`，4/4 通过）：通用 eval 引擎→CONFIRMED(L2)；受限计算器→SUSPECTED(L1)、不误报；纯回显→LIKELY_CLEAN；解释器报错→SUSPECTED(L3)。**待做**：qwed-mcp / pptr-mcp / vegalite / Jij 本地真实靶场端到端 + 并入全量跑。关联 [[code-injection-detection-plan]]。
