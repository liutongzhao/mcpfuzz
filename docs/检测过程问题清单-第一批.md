> 目的：**先登记存在的问题**，供后续优化时对照。本清单只记"现象/影响/证据"，**具体根因与解决方案留待后面逐条深入**（已坐实的根因标注"已定位"，其余标"待分析"）。

## 问题清单

### P1 🔴 序列构建智能体全批次 100% 瘫痪（头号 / 系统性）

- **现象**：370 个需要前置序列的工具（`plan.needs_sequence`），序列构建智能体 **370/370 全部失败**（`agent.limit`）、**零调用**（`agent.done calls:0`）、全部回退到"无大模型"占位（`fallback(无大模型)`）。整批次没有一个多步工具被智能体正常搭起来。
- **影响**：所有需要前置（session / connection / 先建资源）的工具都建不出序列 → 用占位值 `"test"` 硬打 → 判"未触达"。**已知 RCE `send_command.input`（= MCPVULN-001 同款包 @1.0.7）被漏报**：批次确认 0，2026-11-02 重扫仍确认 0（5/5 agent 调用失败）；该参数 sink 已正确标为 command_injection=1.0，只差"建一个合法 session"的临门一脚。
- **证据/量化**：`agent.limit` 370；其中 LLM 中转 `502 Upstream request failed` **333**、`Event loop is closed` **37**；时间上均匀铺满整个批次窗口（非瞬时抖动）。
- **根因状态**：**已定位**。网关（mcphub）给工具名加服务名前缀，服务名是注册表 ID 如 `io.github.amol21p_interactive-terminal`（**带点号 `.`**）；智能体做 function-calling 时把它当 OpenAI function name 发出，但 OpenAI 规范 `^[a-zA-Z0-9_-]+$` **不允许点号** → 上游拒绝 → 中转回 502。实测铁证：`a.b.c`→502 / `a_b_c`→200；带点号真实工具名→502 / 点号换下划线→200；temperature、streaming、function-calling 本身、工具数量均已排除，唯一变量是点号。另：agent `max_retries=1`、无退避、无韧性。
- **✅ 状态：已修复（2026-11-02，第一类）**。`agent.py` 在 LLM 边界把工具名合规化为 OpenAI 合法名（任意非法字符→`_`），调用轨迹再映射回真名（真正的 MCP 调用走闭包里的原始名，不受影响）。验证：批次漏报的已知 RCE `send_command.input` 重扫后被确认，502=0。

### P2 🟠 兄弟必填参数的填充值不合法 → 整个调用在校验层被拒

- **现象**：在打目标参数时，**另一个必填的兄弟参数**用了死占位 `"test"`，遇到格式/类型约束就把**整个调用**拒掉，目标参数的载荷**根本没被评估**。
- **影响**：大量"未触达"其实是败在兄弟参数，不是目标参数本身。与 P1 叠加（P1 建不出合法 session，P2 又让占位 session_id 不合法）。
- **证据**：≥42 条明确是兄弟参数报错（实际更多，受 P6 截断影响低估）。典型：`send_command` 打 `input` 但 `session_id` 要合法会话号；`search_logs` 的 `from` 要 ISO datetime；`add_connection` 的 `hostKey` 要 `SHAN:<base64>`；`memory` 的 `hash` 要精确长度；`sqlike` 的 `dialect` 要枚举（填 test → `unknown dialect`）。
- **根因状态**：现象已明确；"如何构造合法填充值"的具体策略待分析。

### P3 🟡 目标参数形状不适配（数组/对象 vs 标量）

- **现象**：参数本身是 array / record / object，我们塞了标量字符串 → 被拒：`Array must contain at least 1 element` / `expected record, received string` / `Too small: expected array to have >=N items`。
- **影响**：约 **91 条**未触达属此类。现有形状适配只覆盖"标量数组"，未覆盖字符串数组、对象/record、min-items 数组、嵌套结构。
- **✅ 状态：已修复（2026-11-02，第一类）**。`executor.py::_shaped_args` 补 object 塑形 `{key: 载荷}`（数组非字符串元素已在 sink 阶段判惰性）。验证：marin 的 5 个 object 参数（env/pathParams/body/headers/params）从"expected record 未触达"→ 到达 sink。
- **⏭️ 遗留（归第二类·载荷放置策略）**：object/map 的载荷只放在 **value 位**（key 固定为无害的 `mcpfuzz`），**不测 key 位注入**（如 env 变量名、HTTP 头名作为 sink 的情形）。非回归（修复前这些参数全未触达，现至少测了 value 位），但存在 key 位漏报缺口；是否补 key 位探针属"载荷放置/合成策略"，随第二类一起定。min-items 数组、定型对象/嵌套的更完整塑形同属第二类。

### P4 🟡 目标参数有格式约束，但未按格式构造载荷

- **现象**：参数有 `must start with <前缀>` / pattern / exact-length 约束，我们直接发原始载荷被拒。
- **影响**：约 **32+ 条**。对路径穿越等类别，其实可"满足格式 + 夹带载荷"（如 `合法前缀/../../../etc/passwd`），却直接放弃。
- **根因状态**：现象明确；待分析格式感知的载荷构造。

### P5 🔵 sink 推断把数字/标识符参数也标成注入点（精度）

- **现象**：`limit` / `offset` / `timeout_ms` / `port` / `year` / `importance` / `session_id` 这类数字或标识符参数被分配了注入 sink，打了必被类型校验拒（"期望数字"）。
- **影响**：约 **154 条**未触达属此类——既虚增 unreached，又浪费探针预算。
- **根因状态**：属 sink 推断精度问题；待分析。

### P6 🔵 诊断缺陷：未触达原因不可诊断

- **现象**：403 条未触达的 `note` 全部是同一句模板"所有探针均被输入/schema 校验挡下"，且把"样例错误"**截断**，丢失了"错在哪个参数（at `<param>`）"的关键信息。
- **影响**：348/403 无法从 findings 直接判因，必须回捞 run.log 才能分析。**"未触达"目前不可诊断**，掩盖了 P1~P5 的真实分布。
- **✅ 状态：已修复（2026-11-02，第一类）**。`executor.py` 的未触达 note 保留完整错误（400 字），并以 `_blamed_param` 解析报错点名的参数——若是**兄弟参数**则明确标注（"实际被兄弟参数 'X' 的约束挡下"），直接让 P2 可量化。解析器只认校验类错误、`at <param>` 只取末尾字段，经单测确认不把 "at least/runtime" 等普通英文误判为参数。

### P7 🔵 Event loop is closed（asyncio）

- **现象**：每个服务的**第一个** agent 调用触发 `Event loop is closed`，共 37 次。
- **影响**：次要，但与 P1 叠加放大序列构建失败。备忘曾记此 bug"已修"，实际未净。
- **✅ 状态：已修复（2026-11-02，第一类）**。根因：此前每服务新建/关闭各自的 agent 事件循环，而 LLM/httpx 客户端跨服务复用、仍绑在上个服务已关闭的循环上。`core.py` 改为**进程级常驻一个** agent 事件循环（`_AGENT_LOOP`，跨服务共用、`close()` 不再关它），并把 ChatOpenAI 改为**单例**（一个 httpx 客户端复用，避免每工具累积）。验证：2 服务批扫第 2 个服务 loop_closed 从 1→0。

## 归类与进展

- **第一类（代码实现问题）——✅ 已全部修复（2026-11-02）**：**P1、P3、P6、P7**。这些是"方案没问题、代码没兜住"的通用缺陷，修了只是让现有设计正确运转；已逐个用真实运行验证，最大战果是找回了批次漏报的已知 RCE（`send_command.input`）。
- **第二类（方案/算法问题）——待解决，重点是"参数生成"**：**P2（兄弟必填参数的合法填充值生成）、P4（格式/约束感知的载荷构造）、P5（sink 推断精度）**，外加 P3 遗留的**object key 位注入 / min-items / 嵌套塑形**（载荷放置策略）。这些改的是方法论（参数/载荷怎么生成），按"便于前后对比"的原则在改进版统一做。

> 第一类已闭环；下一步进入第二类——核心是**参数生成的解决方案**（合法填充值 + 约束感知载荷 + sink 精度）。
