# 载荷合成模块设计（草案）

> 方案架构中的「模块 4 载荷合成」。上游吃 Sink 推断的软先验，下游按「探针契约」把产物交给判定模块发射。纯架构设计，不含实现代码、不改现有代码。
>
> 关联：`docs/Sink推断模块设计.md`（上游）、`docs/判定方法论.md` / `docs/判定引擎模块设计.md`（下游）、`docs/漏洞类型与检测手段.md`（套件依据）。

## 1. 模块定位与职责

**职责**：给定一个参数的「注入类别软先验 + 发射台基线」，产出一批**自带对照、自带判定契约**的探针套件，覆盖各启用类别的全部适用判定原语与变体。

**不做**：不判定漏洞（判定模块）；不产生诱饵材料（回连 URL / 唯一 marker 仍由 oracle 铸造，载荷只填入——保持解耦）；不决定“测不测某类”（Sink 先验只排序不闸门，本模块据权重分预算）。

## 2. 现状（改造基线）

当前 `payload/core.py` 的做法：
- 输入参数的 `sinks` 标签列表，**过滤 `PHASE1_SINKS={命令注入, SSRF, 路径穿越}`**、按置信排序；
- 每个 sink 读静态文件 `dicts/{sink}.txt`，一行一条载荷；
- **只有 oob / reflection 两个通道**；
- `command_injection.txt` 11 条全是 `curl {{CALLBACK}}` 的 shell 语境变体（**纯回连**，无回显/时延/求值/写文件）；`path_traversal.txt` 读 `/etc/passwd` 靠特征串；`ssrf.txt` 仅一条回连 URL。

**现状硬伤**：
1. 参数注入根本不生成（不在 PHASE1、无字典）；
2. 按单标签门控（无该类标签即不出载荷——git_tag.path 漏报成因）；
3. 过度押回连，命令注入仅 OOB；
4. `Payload` 无对照字段，**差分骨架无法支撑**；
5. 变体手写死，无系统化变体展开。

## 3. 目标设计（改成什么）

### 3.1 输入换成软先验，按预算生成、不门控
消费 Sink 的 `class_weights`（地板+抬升）：**为所有权重 ≥ 地板的启用类别都生成套件**；权重 → 预算（变体数量/原语覆盖广度）；floor 保每类**最小套件**；不再按单标签过滤。

### 3.2 产出升格为「探针（ProbeSpec）」五元组
`Payload` 扩展为探针契约（与判定模块共用的接口对象）：
`(载荷值, 良性对照值, 漏洞类, 适用观测底座, 预期可观测效应, 命中判据, 关联oracle观测物token)`。
- **新增「良性对照值」**：差分骨架的前提——与载荷只差“活性成分”的无害值。
- **命中判据**：该在哪看、看什么（唯一 token 命中 / canary 精确匹配 / 文件特征签名 / 时延差超阈值 / A-B 稳定分化）。
- 命名提示：本模块产物为高层探针契约；现有 oracle 代码里的 `Probe`（token/channel/embed）是其**底层观测物**，探针引用它。

### 3.3 字典重组：按「漏洞类 × 技术原语 × 变体」组织
从“每 sink 一个扁平文件”改为**结构化生成器**：每个漏洞类覆盖其**全部适用判定原语**（见 §4），每条原语再按**变体规则**展开。

### 3.4 差分内建
主动型载荷**必须配良性对照**（时延、信任边界、接受/拒绝、布尔等差分原语）；**直接取证型可不配对照**（回连 token、回显 canary、文件特征签名、跨工具读回等本身即铁证）。

### 3.5 “变异” = 系统化变体展开（静态规则驱动）
程序感知载荷已放弃，不再让 LLM 按具体程序造载荷。变体来自确定性规则：
- **语境变体**（命令注入）：`;`、`|`、`||`、`&&`、`&`、换行、`$(...)`、反引号、单/双/无引号闭合；
- **编码变体**（路径穿越）：`../`、`..%2f`、`%2e%2e`、`....//`、绝对路径等；
- **目标变体**（SSRF）：回环、内网段、各云元数据端点、常见内部端口。

### 3.6 通道扩展（与判定引擎对齐）
载荷要能声明所点亮的观测底座：in-band 回显、带外回连(oob)、timing、cross-tool canary、error-fingerprint、liveness——不止现有 oob/reflection。一条载荷可同时挂多个通道。

### 3.7 预算与覆盖优先
默认发全量套件（原语 × 变体），不因未命中早停；预算由先验权重分配，floor 保最小；可配“研究模式（收齐证据）/常规模式（命中即止）”。

### 3.8 解耦保留
诱饵材料（回连 URL、唯一 marker/canary）由 oracle 铸造、载荷填入；本模块只额外声明对照、命中判据、通道。

## 4. 各漏洞类的套件构成

> “全量”：下列每类把所有适用原语都生成，并对有变体维度者展开。

- **命令注入**：回显 canary（in-band，直接取证）｜求值差分（differential，配对照）｜时间延迟（timing，配零延时对照）｜写文件+跨工具读回（cross-tool）｜带外回连（oob）｜被动错误指纹。× 语境变体。
- **参数注入（新增）**：良性特征选项如 `--version`/`--help`（in-band 特征输出，配普通位置值对照）｜未知选项报错指纹（error-fingerprint）｜写文件选项+跨工具读回（cross-tool）｜前导 `-` 值 vs 转义值（接受/拒绝差分）｜（条件）网络类选项触发 oob。
- **路径穿越**：读真实系统文件 `/etc/passwd` 特征签名（in-band，直接取证）｜越界 vs 基目录内（差分，配对照）｜写穿越+跨工具读回（cross-tool）｜解析后绝对路径泄露（error-fingerprint）。× 编码/深度变体。底线：只读证明越界所需的标准文件。
- **SSRF**：信任边界目标 vs 良性外部（差分，核心）｜全读回带（in-band）｜带外回连+边界语义校验（oob）｜内网时序（timing）。× 目标变体。
- **（第二阶段）查询注入**：布尔差分｜时间盲注｜错误型｜联合/带外。× 方言。
- **（第二阶段）代码注入**：求值差分｜回显｜时延｜带外｜堆栈指纹。× 语言。

## 5. 数据契约（ProbeSpec，概念层）

- `tool` / `param_path`
- `vuln_class`：所属注入类别（确认时用它，不回看参数首要标签）
- `value`：活性载荷值
- `control`：良性对照值（差分原语必填；直接取证型可空）
- `channels`：点亮的观测底座列表
- `expected_effect` / `hit_predicate`：预期效应与命中判据
- `observable_ref`：引用 oracle 铸造的观测物（token/embed），用于需要诱饵的通道
- `rank` / `budget_tag`：排序与预算归属（来自先验权重）

## 6. 与上下游接口

- **Sink → 载荷**：提供 `class_weights`；本模块据权重决定生成哪些类别套件、分配变体预算（floor 保最小）。
- **载荷 ↔ oracle**：需要诱饵的通道，向 oracle 申领观测物（token/embed）并填入；保持“诱饵归 oracle”的解耦。
- **载荷 → 判定/编排**：交付 ProbeSpec 套件；编排器在发射台就绪后逐探针发射，判定模块按 channels/hit_predicate 观测、按差分骨架裁决、确认时用 `vuln_class`。
- **结构契约**：载荷注入目标参数时须尊重参数结构（标量/数组/嵌套对象），由驱动层 `nest_arguments` 统一还原；本模块只产“值 + 对照”，不负责结构摆放。

## 7. 与现有代码的对应（演进方向，不现在改）

- `payload/types.py::Payload` → 扩为 ProbeSpec（加 control / channels / expected_effect / hit_predicate / vuln_class）；
- `payload/core.py::PayloadSynthesizer.synthesize` → 入参改为 ParamSinkPrior；按 `class_weights` 遍历启用类别、按预算生成；去掉 `PHASE1_SINKS` 门控（降级为阶段范围配置、补入参数注入）；
- `payload/dicts/*.txt` → 重组为「类 × 原语」模板 + 变体展开规则（语境/编码/目标）；新增参数注入模板；命令注入补回显/时延/求值/写文件；
- 通道：在 oracle 侧扩出 timing / cross-tool / error-fingerprint / liveness / in-band（现仅 oob/reflection）——与判定引擎模块设计同步演进；
- 遵循 baseline 版计划：方案级改动待基线对比后再落代码。

## 8. 待细化难点

- **对照值的构造规则**：如何对每类/每条载荷自动生成“只差活性成分”的良性对照。
- **变体展开的预算控制**：类 × 原语 × 变体的组合膨胀，如何用先验权重与上限约束。
- **跨工具 canary 的配对**：依赖判定模块识别配套读/写工具（与判定的触达判定协同）。
- **命中判据与通道的标准化**：让一条载荷干净地声明“去哪看、看什么、算不算中”。
