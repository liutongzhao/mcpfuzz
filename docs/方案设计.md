## 1. 研究定位与故事

**目标**：发表论文；首要指标是检测效果，其次是方法的故事性。

**视角**：转向 MCP 背后的服务器本身，检测对服务器及其后端（主机、文件、数据库、下游 API）的危害，**不考虑对智能体的影响**（工具投毒、提示词注入等排除）。这与现有以智能体为中心的 MCP 安全研究形成区分。

**核心故事（一句话）**：
> 经典黑盒 API 测试依赖结构化规范（OpenAPI：类型、响应 schema、状态码）。MCP 把这些结构几乎都去掉了，却多了一样 REST 没有的东西——每个工具都带一段**面向大模型的、必需的自然语言描述和参数说明**。这份本来给大模型看的"说明书"，恰恰是一份精确的攻击面规范。我们把它反过来用，驱动有针对性的注入检测——这是经典黑盒 API 测试做不到的。

**与现有工作的区别**：

| 工作 | 是否需源码 | 是否经智能体 | 载荷 | 我们的差异 |
|---|---|---|---|---|
| VIPER-MCP | 需要（CodeQL 污点分析） | 动态验证经替身智能体 | 进化式提示词 | 我们纯黑盒、不需源码 |
| Exposed by Design | 不需要（黑盒） | 否 | **固定模板**、单工具 | 我们语义驱动、程序感知、多步 |
| 我们的方案 | 不需要 | **否，直接调工具** | 语义/程序感知 + 可验证探针 | —— |

**方法论卖点**：测试时**直接调用工具，不经过大模型智能体**，更快、更确定、可复现。大模型只在"离线理解元数据、生成载荷"时使用，不进入判定回路——以此回应"这不就是提示词工程吗"的质疑。

## 2. 研究范围

第一阶段（原型，MVP）聚焦注入类，先把整条流程跑通、拿到真实漏洞的正反馈，再扩展。

| 维度 | MVP 选择 | 理由 |
|---|---|---|
| 传输方式 | Streamable HTTP（stdio 服务器用网关包成 HTTP） | 支持远程部署与访问 |
| 注入类型 | 命令注入 + 参数注入 + 路径穿越 + SSRF | 覆盖数据中约 342/388；参数注入是差异点 |
| 调用深度 | 单步为主，跨工具判定作为可选 | 注入类约 90% 单步 |
| 判定 | 带外回连 + 标记文件 + 回显 + 时延 | 覆盖上述四类 |
| 代码/SQL/模板注入 | 放到第二阶段 | 判定更复杂 |
| 访问控制类漏洞 | 暂缓 | 先做结构清晰的注入类 |

## 3. 注入漏洞分类（检测目标）

按"用户参数最终流向哪个危险操作（sink）"划分。sink 决定用什么载荷、用什么判定方法。括号内为数据集中目标子集的条数。

| 子类 | 危险操作（sink） | 数量 | 主流判定 |
|---|---|---|---|
| 命令注入 | shell / child_process / os.system | 114 | 回连、标记文件 |
| 路径穿越 | 文件读写 | 135 | 标记文件、回显 |
| SSRF | 出站 HTTP 请求 | 93 | 回连、回显 |
| 代码注入（阶段二） | eval/exec/模板引擎/parse_expr | 18 | 标记文件、回连 |
| SQL/NoSQL 注入（阶段二） | 数据库查询（含 Cypher/KQL/DQL） | 11 | 回显 |
| 参数注入 | 包装的 CLI 程序（git/kubectl/ssh） | 10 | 标记文件、回连 |
| 其他注入（阶段二） | GraphQL / Host 头 / .env / 日志 | 7 | 回显、回连 |

**关键观察**：
- 注入类约 90% 为单步，直接通过 `tools/call` 参数触发。
- MCP 服务器大多是"带认证凭据的瘦包装层"——包一个底层程序/引擎（git、kubectl、数据库、shell、模板引擎），参数几乎原样传下去。注入成功即可拿到服务器持有的高权限凭据。
- 参数注入（leading-dash，如 `--output=`、`-oProxyCommand=`）通用 fuzzer 一般挖不到，是我们的增量点。
- 注入目标语言不止 shell/SQL，还有模板、图查询、KQL、DQL、GraphQL、Host 头、换行注入。

## 4. 整体架构

六个模块 + 数据流：

```
目标 MCP 服务器（Streamable HTTP，远程部署于自建服务器）
        │  initialize / tools/list / tools/call
   ┌────▼─────┐
   │ 1 驱动层  │  连接、拉工具清单、发起调用
   └────┬─────┘
   ┌────▼─────┐
   │ 2 解析器  │  工具/参数/schema/描述 → 内部统一记录
   └────┬─────┘
   ┌────▼─────────┐
   │ 3 Sink 推断  │  每参数 → sink 类型 + 包装程序 + 置信度（大模型 + 规则）
   └────┬─────────┘
   ┌────▼─────────┐
   │ 4 载荷合成    │  基础字典 + 程序感知载荷，注入唯一 token / canary
   └────┬─────────┘
   ┌────▼─────────┐     ┌──────────────┐
   │ 5 编排器      │────▶│ 6 判定/采集   │  回连服务 + canary 目录 + 响应匹配
   │ 填充合法基线 + │◀────│  按 token 关联 │
   │ 替换目标参数   │     └──────────────┘
   └────┬─────────┘
   ┌────▼─────┐
   │ 报告      │  漏洞 + 证据（命中的 token）+ 可复现用例
   └──────────┘
```

## 5. 各模块实现方案

### 模块 1　驱动层
- 使用官方 Python `mcp` SDK 的 Streamable HTTP client，不自行拼 JSON-RPC。
- 职责：连接目标 → `initialize` → `tools/list` → 提供 `call(tool, args)`。
- 需处理：超时、进程/连接异常（崩溃本身是 DoS 信号）、`isError` 标志、把返回内容统一成纯文本串。

### 模块 2　解析器
- 每个工具规整成内部记录：
  ```json
  {"tool":"git_diff","description":"...","params":[
     {"name":"ref","type":"string","required":true,"desc":"git reference","enum":null,"example":null}]}
  ```
- schema 中的 `examples`/`default`/`enum` 保留，供模块 5 填基线值优先使用。

### 模块 3　Sink 推断（大模型主、规则兜底）
- 输入：工具名 + 描述 + 参数列表；输出每参数一条：
  ```json
  {"param":"ref","sinks":["argument_injection"],"wrapped_program":"git",
   "confidence":"high","reason":"git_diff 的 ref 直接拼进 git 命令行"}
  ```
- 规则兜底：参数名命中 `command/cmd/code/path/file/url/host/query/ref` 等，给默认 sink，保证大模型漏判时有下限。
- **可利用性确认（按需，仅对"功能即危险操作"的 sink）**：对 SSRF、路径读这类"参数流到 sink"不等于"有漏洞"的情况，先用良性探针确认 sink 存在，再测能否越界（指向内网/云元数据、跳出允许目录）。对命令注入/代码注入，此步并入攻击阶段。
- 复用 `scripts/llm_config.py` + `swe-2-high`；**注意不要传 `temperature` 参数（该中转会返回 502）**。

### 模块 4　载荷合成
- **基础字典**：从 PayloadsAllTheThings / SecLists / FuzzDB / nuclei 按 sink 类型挑精简子集，落成 `payloads/<sink>.txt`。这部分即"固定模板"基线。
- **程序感知载荷**：对有 `wrapped_program` 的参数，让大模型按程序即时生成（git→`--output=<canary>`，ssh→`-oProxyCommand=...`）。**这是大模型在本系统最该出力、且非"纯提示词工程"之处：它见过大量命令行程序用法，能泛化到未枚举的程序，而非查表。** 消融实验里单独开关。
- **插桩**：每条载荷注入唯一 token。命令注入/SSRF 用 `http://<OOB>/<token>`；路径读用指向 canary 文件的路径，路径写用指向 canary 监视目录的路径。token ↔（工具/参数/载荷）建映射表，判定时反查。

### 模块 5　编排器
- **合法基线填充（关键）**：测某参数时，其它必填参数需先填合理值，否则调用在参数校验阶段就失败、到不了 sink。做法：优先用 schema 的 example/default，否则让大模型按描述生成一组"正常能跑通"的参数。此为能否真正触达 sink 的前提。
- 主循环：对每个工具 × 每个危险参数 × 每条载荷 → 基线参数替换目标参数 → `call` → 给回连留观测窗口后收集信号。

#### 5.1 跨工具取值与生产者-消费者依赖（有状态序列）
很多工具的必填参数，其合法值**只能通过先调用别的工具获得**，自己瞎编会被服务器校验挡在 sink 之前，导致**漏报**（载荷没到达 sink，却判成"未触发"）。这是经典 REST 测试里的生产者-消费者依赖问题，在 MCP 上同样存在，必须在编排器解决。

**真实例子（瑞幸点单 MCP，第一步实测抓到的依赖链）**：
```
queryShopList(经纬度) ─► deptId(门店ID)
      searchProductForMcp(deptId, query) ─► productId / skuCode
      previewOrder(deptId, productList) ─► couponCodeList
      createOrder(deptId, productList, couponCodeList) ─► orderId
      cancelOrder(orderId)
```
其中 `couponCodeList` 的描述明确写了"此参数来自 `previewOrder` 的返回字段"。`deptId`/`productId`/`skuCode`/`orderId` 这类标识符**无法凭空构造**。

**难度分档**：
1. 容易：其它必填参数用 schema 的 default/example/enum 或语法合法常量即可走到 sink（如 git 服务器的 `path` 默认 `.`，自洽，无需别的工具）。
2. 中等：服务器会校验值的有效性，填充值过不了校验 → 需要"看起来真"的值。
3. 困难：真实值只能靠先调**生产者工具**取得（`queryShopList → deptId`）→ 需要有状态的多步调用序列。

**依赖推断的做法（扣住核心故事）**：REST 里靠 OpenAPI 结构硬猜；MCP 的工具描述常把来源用自然语言写出（"来自 previewOrder 的返回"），可用大模型读描述 + 参数名语义，推断"哪个工具的输出能喂给哪个工具的输入"，再按序调用、把真实返回值回填到待测工具。这比 REST 更有抓手，是方法的加分点，也是"有状态序列作为检测手段"的落点。

> 注：此为编排器阶段（模块 5）的核心难点，自建的 git 靶机不涉及（参数自洽），但面向瑞幸这类真实服务器时是必须项。

## 6. 判定方法（Oracle）

核心思路：构造"成功即自证"的**可验证探针**——无论返回文本如何，只要漏洞成立，就产生一个由我们指定、不可能自然出现的可观测信号。

| 信号 | 适用 | 机制 |
|---|---|---|
| 带外回连（OOB） | 命令注入、SSRF、部分代码注入 | 载荷埋唯一子域/路径，指向我方 DNS/HTTP 服务；收到请求=成立。天然支持盲打，最可靠 |
| 标记文件（canary） | 路径穿越、写文件、参数注入写文件 | 读/写带唯一随机串的文件并设法观测 |
| 时间延迟 | 盲 SQL、盲命令 | 载荷令操作 sleep N 秒，测时延差 |
| 回显匹配 | SQL 读、文件读 | 数据/文件内容原样出现在返回中（弱信号，辅助） |

- 判定按 token 关联到具体用例，**目标是零误报**（信号是攻击者指定、不可能自然出现的）。
- 纯大模型语义判定不作主判据（防幻觉），至多作分流。
- **跨工具判定（MCP 特有亮点）**：黑盒远程常"写得进但看不到"，而 MCP 服务器常同时暴露读/写工具——用写工具种 canary、用读工具观测。这是 REST 单接口测试没有的判定能力。

## 7. 部署架构

**自建服务器**：公网 IP `43.133.80.249`，有域名，Ubuntu，已装 Docker。

```
┌──────── 笔记本（只跑轻量编排）────────┐
│  编排器：拉清单、Sink 推断、合成载荷、  │
│  发起 tools/call、看报告               │
│  （大模型调用走中转 API，本是网络请求）  │
└───────┬──────────────────────▲────────┘
        │ HTTP tools/call       │ 查询命中
┌───────▼───────────────────────┴────────┐
│          服务器（所有重活）              │
│  ┌─靶机（每个 MCP 服务器一个 Docker）─┐  │
│  │ 网关(stdio→HTTP) → 漏洞版服务器    │  │ 载荷在此执行
│  └───────────────────────────────┘    │
│  ┌─ OOB 回连采集服务（记录 token）──┐    │
│  └──────────────────────────────┘      │
└──────────────────────────────────────────┘
```

**传输方式**：Streamable HTTP。stdio-only 的服务器用 **supergateway**（Node）或 **mcp-proxy**（Python）包成 HTTP：
```bash
# supergateway 示例（参数以 --help 为准）
npx -y supergateway --stdio "npx -y 漏洞版stdio服务器@版本" \
  --outputTransport streamableHttp --port 8000 --host 0.0.0.0
```

**Docker 部署两种情况**：
- stdio 服务器：容器入口是"网关 + stdio 服务器"，对外暴露 HTTP 端口。
- HTTP 原生服务器：容器入口是服务器本身带 HTTP 传输参数。
- 对外都是一个 HTTP 端口，编排器感知不到区别。

**端口策略**：直接暴露公网端口（用户服务器端口大量空闲、无他人访问）。每个靶机一个外部端口（9001、9002…），需在**腾讯云安全组**放行靶机端口与 OOB 端口（9100）。

**OOB 回连**：采集服务跑在服务器主机，监听 `0.0.0.0:9100`，载荷回连地址 `http://43.133.80.249:9100/<token>`。第二阶段测第三方远程服务器时，用域名做 DNS 外带。

**隔离与重置**：每个靶机独立容器，限制权限/内存/CPU、挂受限可写目录；每轮测试间用容器重置，保证互不污染、可复现。

## 8. 实验设计

### 基准集（ground truth，衡量召回）
- 从数据集中挑：开源 + 可部署 + 有明确漏洞版本与修复版本的服务器，每种注入类型若干。
- 候选（示例）：mcp-server-kubernetes（命令+参数注入）、mcp-server-git（参数注入）、radare2-mcp（命令注入）、各 fetch 类（SSRF）、filesystem 类（路径穿越）。
- 部署**有漏洞的旧版本**，记录其 CVE 作为标准答案。先凑 10~15 个。

### 研究问题
- **RQ1 召回**：基准集上能复现多少已知 CVE。
- **RQ2 零日**：在市场/registry 上大量服务器的**最新版本**上跑，挖新漏洞 → 负责任披露。安全顶会最硬的证据。
- **RQ3 消融**：① Sink 推断 规则 vs +大模型；② 载荷 固定字典 vs +程序感知；③ 各判定信号分别关闭。
- **RQ4 基线对比**：vs 固定模板全灌（仿 Exposed by Design）、vs 通用 schema fuzzer（mcp-server-fuzzer）、vs 经适配层接入的 EvoMaster；VIPER 作白盒上界对照。

### 指标
召回率、误报率、工具/参数覆盖率、耗时、大模型调用成本。多次运行报告方差（可复现性）。

## 10. 风险与伦理

- **"就是调大模型"的质疑**：强调大模型只在离线前端，判定回路确定性；框架骨架（sink→载荷→可验证 oracle 映射）是核心，大模型可替换。
- **可复现性**：载荷与推断结果缓存、固化成数据集一并发布；报告多次运行方差。
- **伦理与合法性**：带外回连、写文件有副作用，主实验在隔离的自建环境进行；测第三方服务器须开源自部署或先获授权，发现问题走负责任披露；论文设伦理声明章节。
