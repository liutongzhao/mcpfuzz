# 顶会论文经验：实验设计与写作范式（安全四大 · 检测工具/框架类）

> 用途：**学习安全四大（S&P/USENIX/CCS/NDSS）"黑盒/API 漏洞检测工具"论文的做法与骨气**，供我们写 §Evaluation、搭论证、选 baseline、堵审稿人反驳点时反复查阅。
> **不绑定我们任何旧 RQ 方案**——这里记的是"这类论文普遍怎么做、为什么这么做能过审"，是方法库，不是任务清单。
> 精读来源（全文已下载 `docs/参考论文/`）：**Witcher**(S&P'23 注入灰盒 fuzz)、**NAUTILUS**(USENIX'23 RESTful 漏洞检测)、**Black Widow**(S&P'21 黑盒 Web 扫描)；参照：**MINER**(USENIX'23)、**Atropos**(USENIX'24)、RESTler、foREST。
> 整理日期 2026-11-06。引号内为原文句式，供直接仿写。

---

## 0. 一句话精髓

这类论文能过四大，靠的不是"工具更强"，而是**把每一个可能被审稿人质疑的点，都提前用一个实验或一句话堵死**。读下来有五条共性铁律：

1. **每个"贡献/组件"都必须有一个实验单独证明它有用**（设计↔消融一一对应）。
2. **低误报要绑定到检测机制本身**，不是"我们误报少"，而是"由构造决定几乎不可能误报"。
3. **对比要工程化地做公平**：统一载荷字典、分解隔离变量、专门做 bias 控制实验、诚实报成本。
4. **Ground truth 必须可核**：用"带可用 exploit 的 CVE"做已知集，人工逐条确认，定义 unique 去重规则。
5. **Scope 用技术理由正当化**，不回避边界——主动说"我们不做 X，因为 oracle 无法统一建模"。

## 1. 论文骨架（排版模板）

三篇安全旗会的切法高度一致：

```
Abstract         —— 利害→黑盒为何难(编号列2-4条)→我们的做法(一句)→硬结果(带数字+点名真实系统)
1 Introduction   —— 漏斗(见§2)；结尾 contributions 列表(每条映射到一个 Section)
2 Background/     —— 关键概念 + Motivating/Running Example(用一个具体漏洞贯穿全文)
  Challenges      —— 显式列 N 个"挑战"(每个一段/一句小标题)，后文技术逐一对应
3 Design          —— 按"挑战→技术"组织，不是系统说明书
4 Implementation  —— 极简：语言/规模/接入(常并进 Evaluation 开头)
5 Evaluation      —— 开篇列 RQ；每个 RQ 一小节；消融+对比+真实世界+(统计)
6 Discussion/     —— Bug vs Vulnerability 之辨；Limitations(逐条、owning boundary)
  Limitations     —— Future Work
7 Related Work    —— 差异化表述：对每个竞品点出"区别轴"(多语言/开源/可得/类别)
8 Conclusion
Appendix          —— 大表、microtest 代码、prior-work 对照表(审稿人"可不读")
```

**关键排版习惯**：
- **Running/Motivating Example 贯穿全文**：Intro 就抛一个具体漏洞(NAUTILUS 的 Confluence OGNL、Witcher 的 post-2 脚本)，Design 用它讲技术，Eval 用它当案例。读者始终有个锚。
- **Contributions 列表 = 阅读地图**：Black Widow 每条贡献都带"present them in Section II/III…"，贡献和章节一一绑定。
- **挑战段用编号小标题**：Witcher 把 4 个挑战写成 4 个加粗句("Detecting the input that triggers…"/"Generating feasible inputs…")，Design 的技术逐一回应。

## 2. Introduction 的"漏斗"逻辑（切入点，最值得抄）

三篇 intro 是同一个漏斗，逐段收窄：

| 段 | 动作 | 原文句式(可仿写) |
|---|---|---|
| ① 利害 | 领域重要 + why-now，用**钱/统计数字**砸实 | "In 2019 alone, Google's bug bounty paid \$6.5 million…"(BW)；"91% of respondents experienced API security incidents in 2021"(NAU) |
| ② 需自动化 | 手工不行，需自动技术 | "it is critical to create automatic techniques that discover…"(Witcher) |
| ③ 现有工作分类+各自死穴 | 把 prior art 分成 white/black/grey-box，**逐类点出致命限制** | "White-box…rely on source code which is not always available"；"black-box…hard-coded strings…thus introducing false negatives…infer from output…introduces false positives"(Witcher) |
| ④ 自造证据坐实 gap | **用自己做的小实证研究论证动机** | "according to our empirical study of 609 vulnerabilities, 499 (82%) require multiple API operations"(NAU) — 再用 OWASP/Rapid7 外部佐证 |
| ⑤ 提出方法 | 一句话点题 + 机制骨架 | "To overcome these limitations, we propose X, a novel … framework that …" |
| ⑥ 挑战预告 | 列"应用到本场景的 N 个挑战" | Witcher page-2 的四挑战 |
| ⑦ 结果预告 | **带范围的数字**(不 cherry-pick 单点) + 点名真实系统 | "141% more vulnerabilities, 104% more operations…23 0-days, 12 CVEs…affect millions of users"(NAU) |
| ⑧ 贡献列表 | 3–6 条，映射章节 | "In summary, we make the following contributions:" |
| ⑨ 开放科学 | 承诺开源代码+数据集 | "we will open source our prototype, dataset, and results upon publication" |

**对我们最重要的两个切入点**：
- **③ 里 Witcher 给黑盒扫描器定了两宗罪：硬编码输入→漏报(FN)、靠输出推断→误报(FP)。** 我们是黑盒，审稿人一定拿这个打我们。**我们的答案就是论文的卖点**：(FN) LLM-sink 推断 + 约束感知载荷合成（不靠硬编码串）；(FP) 求值回显/带外**执行确认** oracle（不靠输出推断）。而且 **Witcher 解决这两宗罪要灰盒插桩("1–5 行改解释器")——这正是我们在 MCP 第三方异构生态里做不到、也不需要做的**；黑盒反而是现实威胁模型下的正解。这是我们 novelty 的现成话术。
- **④ 自造实证研究来立动机**：我们可以用"对 N 个市场 MCP 的测量：X% 的工具把输入直接拼进 shell/路径/URL"这类自产数字来论证攻击面真实存在——比空谈有力得多。

## 3. 实验编排：每篇的 RQ 切法（看"用什么证什么"）

| 论文 | RQ 切法 | 自洽点 |
|---|---|---|
| **NAUTILUS** | RQ1 检测能力 / RQ2 操作覆盖 / RQ3 消融(逐组件) / RQ4 真实世界 0-day | 消融的两个组件 = Design 的两个 annotation = Intro 的两个挑战 |
| **Witcher** | RQ1 消融(两增强技术各自贡献) / RQ2 检出有效性(已知集召回) / RQ3 对比商业+SOTA 扫描器 | 每个"augmentation technique"都在 RQ1 被单独开关验证 |
| **Black Widow** | (按能力)爬取覆盖 / 漏洞检出 + 零误报 / 特征分析 | 三支柱(建模/遍历/跨态依赖)各自在结果里被归因 |
| **MINER** | 主实验 48h×5 + 组件实验 12h + 参数预测/checker 各自消融 | 每个数据驱动组件单独一节 |
| **Atropos** | 覆盖 vs SOTA / FP 率 / 多类漏洞检出 | 10 次×24h，ground-truth 精确算 TP/FP |

**共同骨架 = 四件套**：①消融(证组件有用) → ②已知集准确率(证检得准) → ③baseline 对比(证比别人强) → ④真实世界 0-day(证有真用)。**我们缺哪件补哪件；顺序也可照此。**

## 4. 分实验类型的做法 + "堵嘴"要点

### 4.1 准确率 / 检出（在 ground-truth 已知集上）
- **Ground truth 怎么建**：Witcher"**搜带可用 exploit 的公开 CVE**(so that we could verify the existence)"；Atropos 用"提供 ground truth 的项目(16 个已知 bug)"算**精确 TP/FP**。→ 已知集必须每条可独立复现，否则不能算召回。
- **已知集分两档**(NAUTILUS/Witcher 都这么做)：**合成/植入漏洞的靶场**(NodeGoat/JuiceShop/VAmPI、或 Witcher 自建 10 个 PHP microtest，每个只有一条通往漏洞的路径) + **带 CVE 的真实应用**。前者给干净的"已知答案"锚点，后者给真实性。
- **FP 口径**：NAUTILUS 明确"**漏洞检测里真负例(TN)无法定义**，故 FP 率 = FP/(FP+TP)"(=24.74%，还坦承"可接受，人工能快速筛")。→ 别硬套需要 TN 的指标。
- **逐条人工确认**：Witcher"**we manually confirmed each vulnerability by verifying whether it was exploitable**"；命令注入→证实执行了任意 shell；SQLi→喂给 SQLMap 拿到库控制。→ 报出来的每条都人工核过。(我们"只报人工验证为真 + 执行确认"比这更强。)
- **unique 去重规则**(对比公平必需)：Black Widow 定义"每个注入对应服务端一行代码；同一 SQL 查询的多个表单字段算一个注入(理由：开发者只需改一行)"。→ 去重规则要成文、给理由，否则"bug 数"没法比。

### 4.2 覆盖 / 可达（几乎篇篇的一等指标）
- **为何是一等指标**：审稿人第一问"你到底够到漏洞代码没有"。覆盖低则漏报无从谈起。
- **口径选择要讲理**：Black Widow 选"服务端执行的 LoC(Xdebug)"而非"请求过的 URL"，并解释 URL 口径被 CSRF token 等噪声污染；又说明**不报"占总代码比例"**(总 LoC 难算、含大量不可达安装代码)，改报**scanner 间相对 LoC + 独有/共有分解(A\B / A∩B / B\A)**。
- **我们的黑盒等价物**：没有源码覆盖，用**攻击面覆盖**——触达的工具数/参数数、**成功调用的操作数(SRO，NAUTILUS 的 µEC)**、可达率。把"未触达按原因分桶(校验拒 / 缺前置状态)"升为正文指标。

### 4.3 消融（证"技术不是花架子"）
- **沿"声称的贡献/挑战"拆，不沿代码模块拆**：NAUTILUS 只消融两个 annotation(对应两挑战)；Witcher 只消融两个 augmentation。
- **组件→挑战→指标 一一对应**：NAUTILUS"operation annotation 在**序列复杂**的服务贡献大，parameter annotation 在**格式严格**的服务贡献大——because they are designed to address the sequence/parameter generation challenges accordingly"。还给直接归因数字"**67% 的漏洞只有靠 annotation 才检出**"。
- **变体命名清晰**：Witcher 四配置 AFLR/AFLHR/WiCR/WiCHR(有无 coverage-accountant × 有无 HTTP-mutator)；NAUTILUS 的 NO-ANNOTATION / OPERATION-ONLY / PARAMETER-ONLY。
- **两档数据**：合成 microtest(隔离能力、已知答案) + 真实应用(OpenEMR)。
- **规模小但轮次足**：几十个目标即可，但 **5 次×(8~48h)取平均**，跑**统计显著性检验**(见 4.6)。
- **诚实的负结果**：NAUTILUS"无任何 annotation 时甚至略低于 RESTler/Morest"照写不误——负结果反而**界定并增强**了有界主张。

### 4.4 Baseline 对比（证"有 security delta，不是更快的 fuzzer"）
- **选型与排除都给理由**：Black Widow 为 7 个 baseline 每个写一句纳入理由(SOTA 学术 / 兼容旧研究基准 / 近期常用)，并解释**为何不比商业 Burp**("闭源，特征归因难")。
- **统一攻击载荷字典**：NAUTILUS 把所有 baseline(ZAP/w3af/RESTler/Morest)的载荷都换成同一个 **FuzzDB**，"只改它们的取值策略、不动序列生成策略"——**比的是策略/oracle，不是谁 payload 多**。
- **分解对比隔离变量**：Witcher 造"**BurpPlus-Witcher**"(把 Witcher 爬到的请求喂给 Burp)，使"BurpPlus vs Witcher"的差异只来自**输入生成**、与爬虫无关。
- **专门做 bias 控制实验**(最硬核的堵嘴)：Witcher 担心"BW/WebFuzz 打 XSS、自己打 SQLi/cmd 会让覆盖对比不公"，于是**专门加一组实验**(仿 Enemy of the State 的控制法)把 Burp 的 SQL-only 覆盖并进对手，证明"并进后结论不变(变化<3.3%)"→ 预判反驳并用实验杀死。
- **成本诚实**：Witcher"我们 142 req/s 是最快，但发了 6 倍请求、覆盖并没好 6 倍"——不吹，自曝 tradeoff。
- **时间预算对齐**：统一上限(8h/12h/24h/48h)；承认"跨语言/并行度的时间对比本就难做到绝对公平"。

### 4.5 真实世界 / 0-day（证"真有危害，不是玩具"）
- **0-day 表的标准列**：目标+版本+厂商+**厂商确认**+**CVE/Issue-ID**+漏洞类型+**逐工具检出矩阵**(✓/✗/-)。NAUTILUS 的 Table 3 一眼看出"baseline 全漏、只有我们检出"。
- **厂商确认 + 负责任披露**：NAUTILUS"23 个 0-day，21 个厂商已确认，10 个已分配 CVE，已提交 MITRE"。→ 生态扫出的新漏洞要走确认+披露，才算数。
- **Case study 写成逐步攻击链**：NAUTILUS 的 Confluence OGNL 注入"(1) 注册拿 API key →(2) POST 注入 `{222*3}` →(3) GET 看到 `666` 说明被求值"。
- **PoC 安全化**：NAUTILUS"数学运算载荷只是 **proof-of-concept**；攻击者可换成 `wget resource-url` 做 RCE"——**用无害 PoC 演示，用文字描述真实危害**。(契合我们"容器即宿主"下落 sentinel 即证危害。)
- **bug vs vulnerability 之辨**：NAUTILUS 专门一段"我们不把 HTTP 500 当漏洞…专注可利用的 vuln"；Witcher 脚注"有个 execve 的输入无法判定可利用性，**算 bug 不算 vulnerability**"。→ 这正是我们"真漏洞 vs 本职功能(dangerous-by-design)"必须成文的判定。

### 4.6 统计严谨性（fuzzing 类的硬门槛）
- **N 次 + 方差/均值**：Atropos"**fuzzing 是随机过程，故跑 10 次×24h**"；MINER/NAUTILUS **5 次**取平均"to avoid statistical bias"。单跑一次=轶事。
- **显著性检验点名**：Witcher 用 **Mann-Whitney U 检验**报 p-value(0.01208)；NAUTILUS 表里带 **Vargha-Delaney Â₁₂** 效应量。
- **等 CPU 预算、同种子语料、unique-bug 用 ground-truth 判重**(S&P 实验技能也强调)。
- **LLM 非确定性**(我们特有)：必须**每目标多轮 + 报检测率方差**，固定/记录 temperature 与种子——这是我们版的"随机过程多轮"。

## 5. "低误报"的机制化叙事（对我们"执行确认"最直接的启示）

三篇都把低误报**绑定到检测机制的构造**，而非事后统计：
- **Black Widow**：注入 `<script>xss(ID)</script>`，只有该 `xss(ID)` 真被执行、ID 回到数组里才判漏洞——"**要误报，除非应用主动监听并以正确 ID 调用我们注入的函数**(几乎不可能)"→ FP≈0 **by construction**。
- **Atropos**：开篇就把"大量误报会误导开发者、适得其反"立为靶子，然后主打"**测试集上零误报**"。
- **Witcher**：fault escalation——让注入在**真正的危险 sink**处制造可观测故障，而非猜输出。

**→ 我们的话术**：求值回显 oracle = 唯一 sentinel/算式只有在**服务端真执行**时才回显；带外(OOB)= 只有真发起外连才回收。所以我们的低误报不是"调得好"，是"**非真执行则 sentinel 不可能出现**"——和 Black Widow 同构，写法可直接仿。

## 6. Limitations / Discussion 的写法

- **逐条列、owning the boundary**：Witcher 明说"只做 SQLi+cmd(不做 XSS/PT/LFI/RCE)""只做反射型(first-order)、不做存储型(second-order)""不建模多页状态(一次一个 URL)"——每条都把边界划清。
- **用技术理由正当化 scope**：NAUTILUS"improper resource handling 不做，**因为 test oracle 无法统一建模**(数据敏感度因服务而异)…故我们专注注入类"。→ 不是"没空做"，是"有原则地不做"。
- **Future Work 给出可操作设想**：Witcher"加 LFI/PT 检测可通过(1)每目录放 honeypot 文件 (2)检测新文件落地来 escalate"——连未来工作都具体到机制。

## 7. 措辞 / 句式速查（直接仿写库）

**转折/递进连接词**：Unfortunately, … / However, … / Even worse, … / In essence, … / As a consequence, … thus introducing {false negatives} / Due to these challenges, there exists a {huge research gap} / To overcome the above limitations, we propose … / Therefore, a technique that … is urgently needed.

**主张校准(带范围、不吹)**："improves … by between 63% and 280%"；"an average of 141% more"；"we show that effective coverage is possible with only 1–5 lines of changes"。**永远给区间或 n，不给光秃秃一个最大值。**

**机制化宣称**："free of false positives on the tested applications **thanks to its dynamic verification**"——主张永远挂在机制上、且**限定范围**("on the tested applications")。

**scope 句**："This motivates the focus of this paper on … with particular emphasis on {XSS}."；"Considering these two points, we focus on {injection} vulnerabilities."

**诚实 tradeoff 句**："it issued six times the requests … however, the coverage was not six times better."

**贡献句模板**："We conduct an empirical study to …"；"We propose a novel design of …"；"We implement …"；"We compare … against {N} state-of-the-art … and demonstrate that …"；"We responsibly disclose … and all are confirmed and fixed."

## 8. 给我们论文的直接映射（entry points + 反驳点清单）

**可直接借用的切入点**：
1. Intro ③：把黑盒两宗罪(硬编码→FN、输出推断→FP)摆出来，用"LLM 推断+约束合成"治 FN、"执行确认 oracle"治 FP 作答，并点明"我们不需灰盒插桩(MCP 第三方异构)"。
2. Intro ④：自造一个 MCP 攻击面实证小研究来立动机。
3. Eval 四件套：消融→已知集准确率→baseline 对比→真实世界 0-day，缺哪补哪。
4. 低误报机制化叙事(§5)直接套 Black Widow 的写法。

**写实验前先列"审稿人会怎么驳"，逐条配实验**(仿 Witcher 的 bias 控制实验)：
| 可能的反驳 | 用什么堵 |
|---|---|
| 数字不可信/无 ground truth | 带可用背书(CVE/exploit)的已知集 + 逐条人工+执行确认 |
| 你只是 payload 堆得多 | baseline **统一载荷字典**，只比策略/oracle |
| 对比不公平(类别/爬虫/预算不同) | 分解隔离变量(BurpPlus 式) + **专门 bias 控制实验** + 等预算 |
| oracle/组件是花架子 | 消融：组件→挑战→指标一一对应 + 直接归因数字 |
| 误报一大堆 | FP=FP/(FP+TP) + "非真执行 sentinel 不可能出现"机制论证 |
| 跑一次不稳(更别说 LLM) | 多轮 N≥5 + 方差 + 显著性检验 + 固定种子/温度 |
| 玩具目标/危害夸大 | 真实世界 0-day + 厂商确认 + 逐步攻击链 case study |
| 便利样本不代表生态 | 定义总体/抽样框/覆盖率(这是我们测量贡献的独有战场) |
| 检出的是本职功能不是漏洞 | 成文可辩护的"漏洞 vs dangerous-by-design"判定(仿 bug-vs-vuln) |
| 伤害真实系统/ethics | 自建测试床 + 负责任披露时间线 + 无 IRB 说明 |
