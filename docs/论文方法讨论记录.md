## 一、全局共识（贯穿三阶段）

### 论文定位
- Research paper（非 SoK），投 IEEE S&P。
- **主脊 = 方法**（mcpfuzz 黑盒检测框架）；**测量 = 收益(payoff)**，辅助验证工具能力、揭示攻击面广泛性；**新攻击面(MCP) = 动机框架**。三者**不平起平坐**（平起 = 被拒死法）。
- 【2026-11-11】**novelty / 头牌卖点先不定**——过早钉 novelty（如之前把执行确认 oracle 定为"全文头牌"）会带偏方法和写法的主观判断。各阶段（含执行确认 oracle）照常讨论、照常写，但**先不给谁贴"头牌 / 第一"的标签**；待方法与实验成形后再回头定位。

### 方法框架 = 三个模块（按攻击者脑子里的顺序）
1. **识别（定位）**：哪个参数流进哪类危险操作 —— ✅ 已讨论（见 §三）
2. **构建（到达）**：智能体建前置序列、把目标工具推到可打状态、备好参数 —— ✅ 已讨论（见 §四）
3. **载荷攻击验证（命中-确认）**：执行确认 oracle —— ✅ 已讨论（见 §五）

### 全文脊柱 = 挑战 → 技术 → 消融（一一对应）
> 学自四大论文范式（见 `docs/顶会论文经验_实验与写作.md`）：**同一组挑战在 Intro(预告) / §Challenges(列出) / §Design(技术回应) / §Eval(消融证明) 反复出现、三处咬死对齐**——这是全文行文的总纲。

| 挑战（黑盒 MCP 特有） | 技术（§Design） | 消融（§Eval 证明有用） |
|---|---|---|
| **定位**：无 spec，判不出哪个参数流进哪类危险边界 | 语义参数分类（阶段一） | 语义 vs 关键词 |
| **到达**：深层工具要前置状态、依赖藏在自然语言里、够不到 | 智能体序列构建（阶段二） | 智能体 开 vs 关 |
| **确认**：黑盒外部认不出"真触发"（回显≠执行、本职≠漏洞） | 执行确认 oracle（阶段三） | 差分→精度 / 多位置→覆盖 |

> 内核（把三挑战拧成一股）：黑盒注入两宗原罪——硬编码→漏报、输出推断→误报；我们用 **LLM 语义治漏报、执行确认治误报**，且 MCP 不可插桩故黑盒是正解。另选一个 **Running Example**（一个代表漏洞）贯穿 Intro→Design→Eval。

### 承重墙（堵"每类特判 / 不通用"）
- 两根正交轴：**5 个检测器（每类漏洞一个，固定、可扩展）× 4 个观测位置（带内回显 / 带外回连 / 时延 / 跨工具读回）**；差分是判定方法、所有类都用。
- 一个类 = 一个检测器；通用、非特判、可扩展。

### 框架图
- 画成**带"黑盒膜" + 反馈闭环**的架构图，**不是直线流水线**（直线会坐实"fuzzer 管线 / REST 换皮"）。
- 但也别画成抽象艺术——要让人看懂真实机制、且和各小节一一对应。

### 威胁模型（【2026-11-10 用户纠正，很关键，一定做好、否则没说服力，需配图）
> **网关 / 容器是实验脚手架，绝不写进威胁模型。** 它们是为做实验方便（服务多、逐个部署麻烦，用网关统一管）才加的；"容器=宿主"只用于**测试床里判危害 / 危害闭环演示**（§Implementation/§Eval），不是威胁模型。详见 [[threat-model-container-is-host]]。

论文威胁模型 = **普通、真实的部署**：
- 一个 MCP 服务**部署在某宿主机上、对外只暴露一个端点**供 agent 调用；它就在宿主机上，**不经过网关**。
- 攻击者**只知道一个端点**（+ `tools/list` 的工具名/自然语言描述/入参 schema），看不到源码、不知内部——这就是端点任何客户端的真实视角（= 黑盒前提的来源）。
- 攻击者 = 任何能到达端点者（直接网络可达，或经被操纵/恶意 agent 被授予该工具）；向量 = 构造的工具调用参数。
- 【2026-11-12 作者收窄】**攻击模型 = 攻击者伪装成 MCP 客户端，直接与服务器通信**：MCP 分客户端（在智能体应用内）和服务器，两端按公开协议通信，所以任何人都能实现一个客户端、向服务器发任意参数。**前提假设就是 MCP 服务器对外提供服务**；"能否从外部连上（stdio vs 远程）""有没有认证"都不是本文要证明的问题，不展开。**不讲智能体侧的问题**（不以提示注入为攻击途径），研究对象是服务器漏洞。
- 危害：参数触发服务端注入 → 在**承载该 MCP 的宿主机**上命令/路径/网络/求值滥用 → 读写文件、偷凭据、够内网、RCE。沦陷的是 MCP 自己那台宿主机。
- 不假设网关 / 特殊拓扑——端点可达 + 公开 tools/list 就够攻击。哪怕现实中真经网关，对外人也只是一个端点、不知情。

### 图（figures）——论文要图丰富，且认真设计
- **威胁模型图**（§2）：按上面的"普通部署 + 端点 + 黑盒攻击者"画，重点设计。
- **框架图**（§3）：黑盒膜 + 反馈闭环（见上）。
- **（后话）MCP 协议原理图**：可考虑画一张，说明 MCP 暴露了什么、**为什么黑盒也能检测到东西**。
- **实验图表**：各 RQ 的图表要丰富（准确率/消融/测量分布/危害链路等）。

## 二、作者的要求 / 偏好 / 风格（写论文务必遵守）

1. **论文是论文、工具是工具。** 写宏观方法、讲故事，**不写实现细节**（变量名、阈值、prompt、状态机这些进附录/artifact，不进正文）。
2. **"真改代码" vs "只换说法" 每次都要说清。** 原则上发现更好写法就真改源码对齐；但**本轮阶段一是例外——决定只换论文说法、代码不改**（"分类"替"打分"是合理抽象，不算造假）。往后每个决定都要标明属于哪种。
3. **不堆术语/行话。** 专业词先用大白话解释、或干脆不用；多举具体例子。（已点名反感：可控性门、约束穿透、地板、软先验、fail-open 这类词。）
4. **不接受"换个高级说法包装单薄内容"**（信誉炸弹）；但合理抽象 / 正确的学名可以用。
5. **讨论时点到为止，别反复强调"可信度 / artifact 会穿帮"之类顾虑**——提一句够了，不要絮叨说教。
6. 讨论一律**中文**；不要完全迎合，该顶就顶，但别当杠精。
7. **目前只有 E1 准确率一个实验结果就够了**，不急着铺实验；边讨论边按需补。
8. **论文用词必须规范、专业**：不用口语、不用自造 / 看不懂 / 随意命名的词。反例：别用"兄弟参数""发射台"这类——改用标准说法（如"其余必填参数""基线调用"）。
9. **实验别铺太碎**：抓主要结论，不把一个点拆成一堆细对比。

## 三、阶段一：识别 = 基于语义的参数分类 ✅ 已收口

### 定位（论文怎么讲）
- 一句话：**给定工具名称 + 描述 + 参数结构，对每个参数做分类，判定它的值在服务端能流进哪几类危险操作**（命令 / 参数 / 路径 / 请求 / 查询 / 代码求值）。
- 方法名：**基于语义的参数分类（semantic parameter classification）**。
- 关键：**说"分类"，不说"打分"**。打分 → 按分选，中间阈值无依据，审稿人会问"凭什么 0.7"；分类是"下决定"，干净、可评测。

### 要点
- **多标签**：一个参数可**同时属多类**（如一个 `path` 值既是路径穿越、又被拼进命令行执行 → 命令注入），不是二选一。
- **分类依据两样**：**结构**（schema）管"能不能注入"（枚举/布尔等封闭值域先排掉）；**语义**（大模型读描述）管"归哪类"。
- **输出** = 一组 `(参数, 类)` 对 = 攻击面，定义后面测什么。
- 承重墙在这落地：分类的那几个类 = 那几个检测器。

### 卖点 + 消融（让这节饱满）
- **卖点**：`semantic understanding > surface pattern matching`。不靠关键词/硬编码（换个服务器就漏），靠读懂工具描述语义 → 对任意第三方工具通用。
- **具体例子**（可写进正文）：参数名 `value` / `input` 无危险关键词，但描述写 "the script to execute" → 关键词一无所获、语义一眼归到代码/命令类；反过来名字带 `path` 实为逻辑 ID 的，语义不误报。
- **消融：语义(LLM) vs 启发式(关键词规则)**。代码现成开关 `use_llm`。报两个数：
  - 主（端到端归因）：只用关键词会**漏掉 N 个**语义版能检出的真漏洞（"X 个漏洞只有靠语义分类才测得到"）。
  - 辅（分类本身）：per-class 分类准确率 / 混淆矩阵，解释主指标为什么掉。（正样本 CVE 参数有真类别标签可做诊断。）
- **成本：几乎白来**——不改代码；甚至可能不用重跑（定型日志 `events/sinks` 存有每参数语义分类输出，规则版确定性、离线在同批工具目录重放即可）。
- **白送的评测指标**：分类准确率（打分那套报不出）。

### 论文落点（示例句）
- §Design：*We classify each parameter by semantically interpreting the tool's described behavior, rather than matching surface keywords or structural patterns.*
- §Eval：*Ablating the semantic classifier to keyword heuristics drops detection by N vulnerabilities and sink-classification recall by X%, confirming that semantic understanding is what makes the attack surface recoverable on heterogeneous third-party tools.*

### ⛔ 已弃用的讲法（别再走回头路）
- **"MCP 把类型化契约退化成大白话"** —— 错。MCP 的 `inputSchema` 是完整 JSON Schema（type/enum/required/pattern/format/嵌套），和 OpenAPI 一样有结构。schema 给的是"形状"不是"效果"，但**它确实有结构**，别说 MCP 没有。
- **贝叶斯后验 + 熵 + 信息增益 + 自适应发射** —— 代码是**静态一次性分配**、不是序贯循环，难做又不符，放弃（最多 Discussion 一句 future work）。
- **软先验 / 地板 / fail-open / 可证明召回下界 / propose-and-verify / 强制引证** 当卖点 —— 太像代码细节、已被否。
- **精确派 vs 宁多派** —— 是 prompt 层面的实现细节（分类器偏保守还是偏宽），**不进论文**。

## 四、阶段二：构建 = 智能体序列构建（+ 参数生成）✅ 要讲的点已定（实验讨论中）

> 作者定调：这是**最想重点讲**的一节。视为涵盖了黑盒接口测试的**两大核心难点——序列构建 + 参数生成**，我们用一个智能体把两难**一并**解了。要重点讲、重点做实验证明。
> 代码：闭环智能体已实现（`orchestrator/agent.py`，LangGraph ReAct），一次性规划 `planner.py` 降级为兜底。

### 整体定位
- 输入目标工具 → 输出一条"备好参数、能合法打到它"的调用序列，把"打不到深层工具"这堵前置墙拆掉。
- 方法名候选：**Agentic Sequence Construction（智能体序列构建）**（待定）。
- 框架图：一个智能体图标，"过它之后目标工具可达、参数就绪"；内部不展开。

### 论文里要讲的点（从哪些方面写；本轮不定逐段标题）
1. **问题定义（最花墨、最有深度）**：把"序列构建 + 参数生成"立成严谨问题。必填参数里有些能编（坐标/搜索词/文件名）、有些**编不出来**（不透明 id/令牌/须已存在路径，只能来自前置返回）；有些前置是**副作用状态**（设工作目录/clone），不在 schema；黑盒**看不见工具产出** → 在看不见的空间里搜索。
2. **为什么显而易见的做法都不行（design rationale）**：静态推（依赖在散文里、产出运行前不可知）/ 一次性规划（无执行反馈、猜错不能回头、断在运行时才出现的不透明值）/ 穷举（爆炸且供不出不透明值）——每个失败反推方法需具备的性质。
3. **方法 = 讲它保证的性质，不讲内部循环**：执行驱动的探索 / 增量反馈式构建（上步真实返回流入下步）/ 语义化生产者发现（从工具语义推"谁产出这个值"）/ 目标导向终止（可达 or 可判定不可达；也让"没搭起来"与"搭起来没洞"分得开）/ 良性边界（只调通不攻击、LLM 不进判定）。
4. **参数生成（跟着智能体讲，不单独拔高）**：主角是智能体——它在构建序列的同时产出一次合法调用所需的参数值。**不要**把它包装成"我们有个 LLM 参数生成器"（LLM 只是其余必填参数取值的一个备选，不刻意提）。可**简要列一下参数取值来源**（像 API 测试论文那样列 provenance，但**只提一下、不是重点**）：① 智能体序列构建后从前置响应里得到的值（不可编的那类）；② schema 声明的示例值；③ 有格式/约束要求的参数，生成一个满足约束的值；④ 最后按类型给默认值（字符串给固定串、整数给 1、布尔给 true 等）。
5. **为整套系统买到 measurement validity**：可达性解好，"干净"与"根本没走到"分得开（未测成 ≠ 干净）→ 让召回/精确率有意义。阶段二是让评测诚实的地基。

### 作者的想法 / 本阶段特有约束
- 【约束】**正文不提 REST / RESTler**（讨论时拿 REST 类比，但不写进论文）；相关工作要不要引，以后单独定。
- 【约束】**录制-回放不写**（工程上是好点，论文里没用）。
- 不 claim"多步序列"这件事新；claim 的是"前置挑战" + "创造性地让智能体建前置"。
- 智能体当**黑盒/一个函数**讲；别写 LangGraph/ReAct/预算这些实现。
- 【已澄清的担心】曾担心"太巧思、一个智能体就解决了、没话讲"→ 内容在"问题多难" + "证明真解决"，**不在智能体内部**，够写满一节。

### 实验（目标 = 主要证明智能体的效果；不拆序列/参数两半，不做三臂）
- **主消融（归因）**：开智能体 vs 关智能体（关 = 退回一次性规划 / 单步）→ **X% 已检出漏洞只有靠智能体才到得到、否则漏掉**。这一条同时就是"闭环 vs 开环"的证据（关掉 = 开环），不再单列。
- **可达率** + 平均序列长度 + 多少目标需非平凡序列（撑动机 + 量化解得多好）。
- **多轮 + 方差**（LLM 非确定）；可加"同一目标跨轮可达一致率"堵"跑一次成"。
- **失败归因分桶**（无生产者/终止错误/停滞/预算；代码已 emit，几乎白来）。
- 一个 3–4 步前置链的**走通深例**。
- 注：部分数据可能从定型归档 `events/sinks` 复原（见 [[detection-logs-archive]]）。

## 五、阶段三：载荷攻击验证 = 执行确认 oracle ✅ 要讲的点 + 实验已定

> 核心不是"准备了很多载荷"，是**在黑盒外部可靠确认"漏洞真的触发了"**。（它在全文的分量先不定，见 §一"novelty 先不定"。）

### 核心结构（讨论敲定）
- **探针（probe）= 载荷 + 绑定的观测位置 + 命中判据 + 良性对照**。载荷与确认**协同设计**：每条载荷都有目的——造它时就决定了"若漏洞为真，效应在哪个位置、以什么形态冒头"。不存在"只发不看"的载荷 → 这是"不是载荷字典"的根本。
- **4 个观测位置（证据从哪冒头，平级）**：带内回显 / 带外回连 / 时延 / 跨工具读回。
  - 错误指纹并进带内、不单列；崩溃 / DoS 不做、删掉。
- **差分（判定规矩，套在所有观测位置上，不是第 5 个位置）**：每发攻击都**配一条良性对照**（只差危险成分、其余一样），判决只认"攻击有、对照没有"的差异，不看绝对值。差分在**攻击验证时、逐参数**发挥作用；每判一次有没有漏洞，都是靠这一对的差异。
- **检测器 × 观测位置（承重墙）**：检测器按危险边界分（5 类：命令 / 参数 / 路径 / SSRF / 代码），每类用哪几个位置见下表；同一套位置 + 同一个差分服务所有检测器 → 通用、非特判、可扩展。

### 二元映射（每类用哪几个观测位置；差分所有类都用、不进表）
| 漏洞类型（边界） | 带内回显 | 带外回连 | 时延 | 跨工具读回 |
|---|---|---|---|---|
| 命令注入（shell） | 用 | 用 | 用 | 用 |
| 参数注入（argv） | 用 | 不用 | 不用 | 用 |
| 路径穿越（文件系统） | 用 | 不用 | 不用 | 用 |
| SSRF（网络发起） | 用 | 用 | 用 | 不用 |
| 代码注入（求值） | 用 | 用 | 用 | 用 |

读法：带内回显所有类都用；边界越通用（shell / 求值）位置越多，越专一（文件系统不触网 → 无带外 / 时延）越少。查询注入二期、不列。

### 论文里要讲的点（从哪些方面写）
1. **确认的难题**：黑盒里发载荷易、**确认难**（不插桩、无日志）；两个坑——回显 ≠ 执行、本职功能 ≠ 漏洞。
2. **探针抽象（反"载荷字典"）**：单位是探针不是载荷；载荷与确认协同设计、每条有目的。
3. **4 个观测位置**：抽象介绍（效应能从哪冒头）；穷尽黑盒可观测面；至少一个不依赖出网（带外被禁也不整类失明）。
4. **差分**：成对发、只认差异 → 解决两个坑（本职功能 / 噪声）、带来语义正确性。
5. **检测器 × 位置（承重墙）**：通用、非特判、可扩展（加一类 = 加一个检测器，复用位置与差分）。
6. **与旧工作划清界限**：旧黑盒注入工作多为"带外回连一命中即确认"的**单信号**；我们 = 多位置 + 差分 → 更全（覆盖）、更稳（不依赖出网）、更可信（差分杀本职功能 / 噪声误报）= security delta。

### 不写（按作者定）
- **证据分级 / 五态判决**：工程问题，不进正文。
- **"相互印证"搁置**：它只是"多位置一致"这个性质，不作为与差分并列的方法硬塞。
- 具体载荷串：进附录 / artifact。

### 实验（目标 = 证明 oracle 的两样价值：精度靠差分、覆盖靠多位置）
- **差分消融 → 精度**：关掉差分（按绝对观测判、不比对照）→ 误报暴涨（本职功能 / 噪声 / 回显被误判成漏洞）。证明差分是精度的来源。
- **单位置 vs 多位置 → 覆盖 / 召回**：只留单个观测位置（尤其"只留带外"= 旧工作做法）→ 召回掉多少、哪些漏洞只有某个位置抓得到 → 证明多位置互补、不冗余。
- 注：两条都可能从定型归档 `events/sinks`（按探针 / 通道记了命中）离线复原，几乎不用重跑。见 [[detection-logs-archive]]。

## 七、对比实验（RQ2 · baseline）✅ 选型已定（2026-11-11）

> 背景：做了一轮 prior-art 调研（报告在 `reports/MCP 黑盒检测 baseline 调研.md`，原始笔记在 `research_notes/MCP 黑盒检测 baseline 调研/`）。结论：**"首个黑盒 MCP 服务端注入检测"不能再说**——已有工具/论文在做几乎同一件事。

### 定下来的选型（作者拍板）
- **正式对比只跑两个工具：`mcpsnare` + `Corvus`。** 其余一律进相关工作、只提不跑。
- 理由：这两个是**唯一能和我们同条件同台**的——都是活体黑盒、走 HTTP、能批量、结果能折成"每台一个是/否"。
- **不做**：LLM-only / 裸 agent 稻草人 baseline（作者定：不需要）；McpSafetyScanner、PortSwigger Burp 扩展、白盒 VIPER/BiFlow/MCPInspect、REST 近亲 VOAPI2/NAUTILUS、描述级 Snyk/Cisco 等 → 全部只进 §Related Work。

### 统一口径（关键 —— 这样才可比）
- **不按漏洞类分、不给 CVE 分类**。每台服务器只问一件事：**这个工具报没报出这台有漏洞**。
- 正样本统计检出（召回），负样本统计误报。服务器级二元 TP/FN/TN/FP（和我们本来的口径一致，见 [[paper-reporting-convention]]；也正是 VIPER 的服务器级口径）。
- 一张表：我们 vs mcpsnare vs Corvus,各报 检出数 / 召回 / 精确率 / 误报。
- 好处：**绕开"各工具覆盖类别不同"**——工具覆盖少 / 确认弱,自然体现为召回低,不用特殊处理（如 Corvus 无代码注入/参数注入、mcpsnare 无参数注入,都直接落在数字上）。

### 公平性前提（跑之前必须守住）
- 每个工具都要**真有机会打到每一台**：连得上端点、带外设施配好、该开的注入模块开了。漏检必须是"工具能力不够",不能是"我们没配好环境",否则会被审稿人抓。
- 上全量前,先验证每个工具在"该能检出的"服务器上至少能检出几个,再跑 44/24。

### 两个 baseline 的配置坑（已查实）
- **mcpsnare**（PyPI,MIT,无论文；走 stdio+streamable HTTP；JSON/SARIF 带 CONFIRMED/FIRM/TENTATIVE → 取 CONFIRMED/FIRM 为"有"）：远程 OOB 要 `--oob interactsh`（默认 `--oob local` 只收 localhost 回连）→ 指到我们自己的带外端点,否则 SSRF/盲命令注入漏报、对它不公平。批量=自己写循环。
- **Corvus**（CobaltoSec,arXiv 2608.00150,MIT；走 HTTP/SSE；自带 `corvus batch targets.yaml`,`--fail-on`/`report.json` 出二元）：**只开注入模块**（`cmd-injection`/`ssrf`/`endpoint-probe`/`cursor-probe`），**绝不开 DoS 组**（`proto-fuzz`/`batch-dos`/`cancellation-probe`/`response-flood`）——我们不做 DoS、且共享网关,会连累同批服务。注意它确认偏回显匹配（README 自曝 MCP05 大量回显误报）、无带外回连——这反过来是我们 precision 论点的佐证。

### "首个"措辞 ——【2026-11-11 暂不定】
- novelty / "首个"的正面说法**先不敲定**（见 §一：过早钉 novelty 会带偏判断）。待方法与实验成形后再回来定。
- 只先记一条调研查实的**硬约束**："**首个黑盒 / 动态检测 MCP 服务端注入**"**不能说**——mcpsnare / Corvus / PortSwigger / mcpsec / MCPwn 都在做动态黑盒（见调研报告）。
- 风险提醒：GitHub 上已有别人的 `mcpfuzz` 同名工具 → **我们工具投稿前建议改名**。
