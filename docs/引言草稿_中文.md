**1 引言**

模型上下文协议（Model Context Protocol，MCP）【引】让大语言模型智能体通过统一的接口调用外部工具。一个 MCP 服务器部署在宿主机上，对外暴露一个端点；任何连接到该端点的客户端都可以列出服务器提供的工具，并以自己构造的参数调用它们。这些工具常常直接操作宿主机：执行 shell 命令、读写文件、发起网络请求、对表达式求值。调用方提供的参数如果未经妥善处理就流入这些操作，服务器就存在服务端注入漏洞。利用这类漏洞的攻击者不需要任何内部权限，只要能到达端点（直接通过网络，或借助一个被操纵的智能体），就能通过构造的参数在宿主机上执行命令、读取凭据、访问内网。图 1 是一个真实案例：在【CVE-xxxx】中，攻击者【先调用工具 A 取得 X，再在工具 B 的参数 p 中注入……，最终在宿主机上执行任意命令】。

这类漏洞已在 MCP 生态中大量出现。我们收集了截至【日期】公开的【N】个 MCP 服务器相关 CVE，其中【X%】属于注入类；在注入类中，命令注入、参数注入、路径穿越、服务端请求伪造（SSRF）和代码注入五类合计占【Y%】（§2.2）。这五类有一个共同点：漏洞被触发时，服务端执行了攻击者的输入，执行的效应能够从端点外部观测到。访问控制类漏洞（占【Z%】）则不同，它的判定依赖每个服务器各自的权限语义，无法用统一的标准判定。因此，本文聚焦于从端点出发检测上述五类注入漏洞。

从端点出发，是检测者在现实中常见的处境。市场上的 MCP 服务器有相当一部分以远程服务的形式托管，或者不公开源码；即使开源，也分散在 TypeScript、Python、Go 等多种语言和框架中【数据/引】。面向源码的白盒分析【VIPER-MCP 等，引】因此只能覆盖其中一部分；而且它给出的是从参数到危险操作的潜在路径，不能证明漏洞在运行中真的能被触发。另一类工作只分析工具的描述文本【引】，不运行服务器，无法判断参数是否真的流入了危险操作。已有的黑盒扫描器 mcpsnare【引】和 Corvus【引】直接调用运行中的服务器，【待核实：对每个工具单独调用一次，填入固定的攻击载荷，再根据响应内容判断是否命中】。单次调用到达不了需要前置状态的工具，造成漏报；仅凭响应内容判断，又会把载荷的原样回显和工具的本职功能当成漏洞，造成误报。

在 MCP 上做好黑盒检测，需要解决三个难点（§3）。端点提供的信息只有三样：工具名、写给模型看的自然语言描述、参数的结构定义（JSON Schema）；服务器的实现、工具之间的依赖、服务端的执行过程都不可见。三个难点都由此而来。

- **定位。** 参数的结构定义只描述值的形状，不描述值的去向：名为 `value` 的字符串可能被拼进 shell 命令，名为 `path` 的字符串可能只是一个逻辑标识。检测者需要在看不到实现的情况下，判断每个参数会流入哪一类危险操作。
- **到达。** 许多工具只有在前置状态满足时才会执行到危险操作：会话标识、仓库路径这类参数值只能来自其他工具的返回，而这种依赖只写在自然语言描述里，其他工具会返回什么，也要真正调用之后才知道。检测者需要先构造出一条合法的调用序列，才能把攻击载荷送到目标参数。
- **确认。** 服务端是否执行了注入，在端点外部不可见：载荷出现在响应中，可能只是原样回显；执行命令的工具执行了命令，可能只是在履行本职功能。检测者需要根据外部可观测的现象，判定注入确实被执行了。

我们的方法基于两个观察。第一，MCP 端点虽然不暴露实现，却暴露了专门写给模型阅读的描述。工具的用途、参数的含义、调用的前提都以自然语言写明，因为 MCP 正是依靠模型读懂这些描述来正确调用工具。定位和到达所需的信息就在这些描述里：大语言模型能够读取它们，真实调用的返回则能检验读取的结果。第二，注入一旦被执行，就会在服务端之外留下痕迹：响应中出现的计算结果、发往外部的连接、可测量的响应延迟，或其他工具能读到的状态变化。只要每次攻击都配一个只差危险成分的良性对照，就能把痕迹归因于注入本身，而不是工具的本职功能或环境噪声。

基于这两个观察，我们设计并实现了【工具名】，它分三个阶段依次解决上述难点（§4）。第一阶段是语义参数分类：根据工具名、描述和参数结构，判定每个参数的值可能流入哪几类危险操作，得到待测的（参数，漏洞类型）对，以此解决定位难点。第二阶段是智能体序列构建：智能体从工具描述中推断目标工具依赖哪些前置调用，实际执行这些调用，把真实返回值用于后续调用，直到能够合法地调用目标工具，以此解决到达难点。第三阶段是执行确认：对每个（参数，漏洞类型）对发送探针。每个探针由攻击载荷、预期效应出现的观测位置和一个良性对照组成；只有攻击调用产生了效应、而对照调用没有产生时，才判定漏洞存在，以此解决确认难点。

我们在由 68 个 MCP 服务器实例构成的数据集上评估了【工具名】（§6.1）。其中 44 个实例存在经 CVE 或独立公开报告背书的漏洞，另外 24 个是对应的已修复版本。【工具名】检出了 44 个有漏洞实例中的 32 个（召回率 72.7%）；它报告有漏洞的 35 个实例中，32 个确实有漏洞（精确率 91.4%）。在同一数据集上，mcpsnare 和 Corvus 分别检出【a】个和【b】个，误报【c】个和【d】个（§6.3）。消融实验表明三个阶段缺一不可：分别去掉语义分类、序列构建和良性对照，会导致【x】、【y】个漏洞漏检和【z】个误报（§6.4）。我们还用【工具名】扫描了【M】个公开的 MCP 服务器，发现并人工确认了【K】个此前未知的漏洞，均已向开发者负责任地披露；其中【J】个已获确认，【L】个已分配 CVE 编号（§6.5）。
